## Problem

Verified on `development` @ `e56740c` (originally `11b264a7`; the cited lines are unchanged).

1. **"Large" is not a decision.** The single owner-turn decide (`decision/owner_turn.py::decide_owner_turn` on `development` @ `d85c9d4`, via `agent/request_routing.py::evaluate_request_route`) yields route, tier and `persona_intent` (`OwnerTurnDecision`). Nothing decides "this prompt is a multi-part large task". The only related signals are:
   - `policy.local_complexity_tier` (`decision/policy.py`): tier 4 for expert hints or more than 4000 chars, tier 3 for complex hints or more than 1200 chars.
   - The separate `complexity_escalation` surface (`decision/surfaces.py::complexity_and_escalate`).
   - #649's regex `is_large_request` (`agent/task_workflow.py`, landed), which is not a reflex decision. It only triggers #649's model planner inside `_run` (`loop.py`).
2. **No immediate load of the large model.** `prepare_answer_route` only runs when the loaded model is an orchestrator, or tier ≤ 1 (`agent/loop.py`), and it runs inside `_run`, after the front lane. A large prompt starts on whatever model is loaded. The swap to the large model happens later, if it happens at all, through `execute_visible_model_switch` (`inference/model_escalation.py`).
3. **No large-task ack.** `create_task` publishes the generic `task_acknowledgement(prompt)` as an `acknowledgement` event (`loop.py`), and it is not spoken. As #663 found, `publish_owner_text` goes to `OWNER_CHAT_CHANNEL` (`persona/chat_delivery.py`), and no client reads that channel. The only path the live UI speaks is a `chat_tts` event on the task stream: `useTaskSpeech.ts::useTaskSpeech` → `queueChatSpeech`, mounted in HUD chat and Chat.
4. **The prompt is split only for a dead endpoint.** `agent/intake.py` has a sequential chain:
   - `MAX_SEQUENTIAL_PARTS = 8`, `part_prompt`, `advance_chain`.
   - Chains are stored as JSON files under `data/intake_chains`.
   - Its only caller is `persona/owner_chat.py`, the `stream_owner_chat` endpoint, which has no client.
   - Chat sends go to `/api/tasks`. Since #649, `_run` asks the loaded model for a 1-8 step plan when `is_large_request` fires (`loop.py`, `task_workflow.py::prepare_workflow`). That plan is model-generated, so it isn't a split of the owner's text. It runs on whatever model is loaded, with no completeness check, and a planner failure fails the task (`task_workflow.py::prepare_workflow`).
5. **No completeness check.** No section-level check or bounded iteration exists anywhere.
6. **Durable prompt stages exist (landed #649), but only one task at a time.** `TaskPromptPlan` / `TaskPromptStep` (`db/models.py`) are executed one stored prompt at a time inside one task (`loop.py::AgentRuntime._run`, completion guard `AgentRuntime._update`). Its planner asks the model for the plan (`PLAN_SYSTEM`, `task_workflow.py`), which needs a capable model already loaded. It has no notion of a parent with one child task per section, no section completeness, and no mandatory deeper/quantitative steps.
7. **No queue that runs owner prompts one after another.**
   - `mobile/scheduler.py::tick` runs periodic automations. It skips while the previous run is non-terminal and is admitted by `automation/breaker.admit_automatic_trigger`.
   - `agent/queue_watcher.py` is a file drop queue.
   - #670's `DevelopmentScheduler` (`agent/development_scheduler.py`, `class DevelopmentScheduler` and its `tick()`, whose `resource_hold` dispatch gate is in `tick()`) is a draft and reserves Ollama for Grokbot work.
   - None of them takes N owner sub-prompts and runs them in order.
8. **No guaranteed deeper or quantitative work.** #649's steps are `work` plus `REVIEW_STEPS` (bugfix, fact_check, quality_control; #649 `task_workflow.py`). Nothing requires a deeper-analysis or quantitative sub-task, and nothing validates one.

## Decision

Ship **one RFC with seven implement slices (S0-S6)**, one named model per slice and fast mode off. Nothing waits for #670. #649 has landed and is reused.

**Pipeline at a glance.** A large owner turn becomes one **parent task** (the one the HUD is already following) and N **child tasks**, one per section, run strictly one after another.

```
owner turn ─► decide_owner_turn: large-prompt precheck on the FULL raw prompt (outside the 50 ms window)
   │           ─► _decide_sync: one decide (riders large_prompt / large_prompt_split only when 0232's RE helper did not match)
   │           ─► _apply_floors: 0232 RE floor, then 0245 large floor
   │ large (and not RE)
   ├─► create_task: 0230 prewarm_worker + route decision ─► 0232 RE dispatch (not taken) ─► Task row ─► 0218 S3b persona block
   ├─► 0245 large branch: cancel 0230's pending 9B prewarm; read the RFC-0225 gate outlook (in memory, no probe)
   ├─► ONE spoken ack: the parent's front-lane line (fixed text, chat_tts, 0230-S0 mark lane "front"), worded from the gate outlook
   ├─► preload task started (not awaited), only when the outlook allows: request lease → apply_runtime_profile_to_settings(persist=False) + MANAGER.load(task_id=parent) → warm
   └─► parent runner (after the ack): split → completeness rounds (≤ 3) → compile → persist → await preload (≤ 180 s, defined fallback)
          → dispatch part 1 as a child task (breaker admit + bind)
child terminal hook ─► completed: dispatch next │ failed: stop, parent fails visibly │ needs_owner: parent waits (27B released after idle_unload_seconds)
last part done ─► parent completes with the combined result ─► release lease ─► restore the owner's saved selection ─► schedule_orchestrator_restore (NINE_B_REWARM, public API)
```

Between the ack and the parent's terminal outcome the parent speaks nothing (CoS ruling 5): progress, gate and needs_owner lines are visible events only.

### Terms

| Term | Meaning |
| --- | --- |
| **Large turn** | An owner turn whose decision has `large_prompt == "large"`. |
| **Pipeline** | One `large_prompt_pipelines` row, keyed by the parent task id. |
| **Section / part** | One `large_prompt_sections` row. Its child task runs one detailed prompt. |

### 1. Detection: one decide, two riders (S1)

Detection follows the RFC-0218 pattern: rider questions on the existing decide, no second decide.

**Precedence (CoS ruling, normative, verbatim):** A turn whose prompt contains an absolute filesystem path together with RE intent (RFC-0232's narrowed dump/extraction detection) routes to reverse engineering and is never split by RFC-0245; a path with a plain or coding question routes normally.

Mechanically (D2 + CoS ruling 2026-10-20): RFC-0232 S2's precedence is a **floor in `_apply_floors`** (`owner_turn.py`), not an early return. Every turn keeps the persona precheck (`_decide_sync`) and **exactly one `decide()`**. **0245 adds no RE detection of its own.** RE intent is decided only by RFC-0232 S2's helper `planning.re_intent_match(prompt, *, allowed=None) -> ReIntent | None` (memoised per turn) and its on-disk probe `planning.probe_dump_target`, specified in #664 and not restated here. What 0245 relies on, as #664 guarantees it:
- the probe is admit-first through `store.admit_allowed_target` (#661, landed `bd2558bd`, `reverse_engineering/store.py`), which runs before any stat of the target or a marker, so an outside path makes zero filesystem calls;
- the helper and the probe always read the owner's allow-list from settings (`load_settings().allowed_directories`) and never pass `None` to the gate (`admit_allowed_target(target, None)` is the deliberate trusted-in-process bypass, `store.py`, and is not changed); an empty list admits nothing;
- explicit owner wording skips **only** the dump-marker requirement, never the allow-list check or the source-tree veto.

0245 consumes the result in exactly one place, the precheck, and the floor order:
- **Precheck (one place only):** `large_prompt.precheck(text, settings)` runs in `decide_owner_turn`, **inside** the `try` at `owner_turn.py` and before the worker is submitted, i.e. outside the 50 ms `wait_for`. It calls `planning.re_intent_match(text)` once (the per-turn memo means 0232's own floor reuses the same result) and stores `re_match`. When it matches there is **no candidate**: no rider is appended to the one `decide()`, and `large_prompt_floor` is not set. The local is named **`large_precheck`** so it never collides with the persona `precheck` inside `_decide_sync`. #664 states the same placement. **Timing (N2):** `started = now()` (today `owner_turn.py::decide_owner_turn`) is re-taken **after the last owner-turn precheck**, so no precheck counts against the 50 ms decide budget on the real or the injected clock. Today, with 0245-S1 alone, that is `large_precheck`. RFC-0233-S1 (#668, §1 "Detection", its precheck paragraph) inserts `gap_precheck` after `large_precheck` and **before** the re-take, so the re-take stays the last statement before the decide worker is submitted. 0245-S1 writes it with that comment (`# re-taken after the last owner-turn precheck`). The large precheck has its own bound, **`LARGE_PRECHECK_BOUND_MS = 30`** (`decision/large_prompt.py`): ≤ 20 ms for the rules on a 100 KB paste plus #664's ≤ 10 ms probe wait. It bounds `large_precheck` only; #668's `gap_precheck` keeps its own < 1 ms bound, and neither is charged to the decide budget. It is synchronous and cannot be interrupted; an overrun is logged once with the measured ms and the result is still used (`test_precheck_within_own_bound`).
- **Total:** the precheck never raises. Any exception (its own or the probe's) yields `LargePromptPrecheck(floor="standard", re_match=None, rules_fired=(), mode="sections", error=repr(exc))` and one log line, so `decide_owner_turn` never falls through to `request_routing.py::evaluate_request_route`'s bare decision and today's route plus 0232's floor still apply.
- **Floors:** `_apply_floors(user_message, baseline, literal, result, *, large_precheck=None)` gains one keyword, passed at all three call sites (normal, timeout and exception tails). 0232's RE floor runs first and 0245's large-prompt floor after it; when the RE floor applied, `large_prompt` stays `None`. The verdict is set in `_apply_floors` only; there is no separate deadline helper.

RFC-0232 S2 owns the RE-side test `test_path_plus_re_intent_routes_to_re_before_large_prompt_split` (`tests/test_rfc0232_intent_and_alias.py`). 0245-S1 adds its side of the contract (S1 tests), and `test_one_decide_per_turn` (S1) asserts exactly one `decide()` for a large turn and for a path-plus-RE turn.

- **Precheck on the full prompt (rules, sync).** Reflex runs the rules adapter on `compact_state(raw_state)` (`reflex.py::decide`), which cuts every string over 800 chars to 800 (`decision/types.py`). So size rules are **never** evaluated inside `decide()`. `large_precheck` is computed on the raw `user_message` (placement above) and carries L1-L5, the split mode, `rules_fired`, `floor` (`large` | `standard`), `mode` and `re_match`. It is passed as the keyword `large_precheck` to `_decide_sync`, `_deadline_rules_result` and `_apply_floors`. Cost is linear in the prompt with one regex pass per rule: `test_precheck_bounded_on_100kb_prompt` bounds it.
- **Candidate (inside `_decide_sync`, before the one `decide()`).** A candidate exists only when **all** of these hold:
  - `large_precheck.re_match` is not set (RFC-0232 S2's helper did not match);
  - the baseline route is managed (`baseline.kind == MANAGED_TASK`), and `infer_rules_reply_shape(text)` is none of literal, clarify, self_status, basic_qa or social (all in `REPLY_SHAPES`, `owner_turn.py`);
  - `security_role == ""`;
  - `settings.large_prompts.enabled` is true;
  - `large_precheck.floor == "large"` (at least one rule below fires).

  Without a candidate, no rider is appended and the decision is unchanged byte for byte.
- **Riders (appended to `OWNER_TURN_QUESTIONS` for that call only):**
  - `large_prompt`: choice `standard` | `large`, `decision_class="complexity_escalation"`.
  - `large_prompt_split`: choice `sections` | `questions`, `decision_class="workflow_branch"`.

  Both classes are already in `REFLEX_DECISION_CLASSES` (`decision/types.py`), so the unlisted-class check at `reflex.py::decide` passes. The rules adapter's rider branches (`decision/adapters/rules.py`, next) read only the scalar state keys `large_prompt_floor` and `large_prompt_rules` that `_decide_sync` sets from `large_precheck`; they never measure text.
- **Rules (computed by the precheck on the raw text).** `large` fires if any of these holds:
  - **L1:** `len(prompt) ≥ 4000`.
  - **L2:** at least 3 list items (`^\s*(\d+[.)]|[-*•])\s+`) and `len ≥ 600`.
  - **L3:** at least 3 question sentences (ending in `?`, or starting with an interrogative word in en/nl) and `len ≥ 200`. This also sets split `questions`.
  - **L4:** `task_workflow.is_large_request(prompt)` (landed #649, `agent/task_workflow.py`), imported and called as is, **counted only when `len ≥ 600` or another rule also fires**. "Make a quick snake game" is therefore not large.
  - **L5:** `local_complexity_tier(prompt) == 4`.

  Split mode: `questions` when L3 fired and fewer than 3 list items exist, otherwise `sections`.
- **Floor semantics** (the rule at `reflex.py::decide`: providers may raise a tier but never lower it):
  - `decision/owner_turn.py::_apply_floors` applies `large_precheck.floor` (`decision/reflex.py::decide` does not see `large_precheck`; it only reads the rider scalars). A typed provider may raise `standard → large` only at confidence ≥ 0.75, and may never lower `large → standard`.
  - **Deadline and exception fallbacks keep the verdict and the full question.** `_deadline_rules_result(..., large_precheck=...)` asks `OWNER_TURN_QUESTIONS` plus the riders when a candidate exists, and the `TimeoutError` / `Exception` tails reach the verdict through `_apply_floors(..., large_precheck=large_precheck)`. The owner's full text reaches `create_task` unchanged (it is the `prompt` argument, never rebuilt from the projection), so `Task.prompt` holds the whole question.
  - A provider's split answer wins only when L3 did not fire.
- **Final gate after the floors.** The verdict is nulled when 0232's RE floor applied, and unless the final route is `managed_task` and the final reply shape is not in {literal, clarify, self_status, basic_qa, social}. A provider that answers `direct_reply` at ≥ 0.75 on a 4500-char prompt therefore leaves `large_prompt is None`, as today.
- **Engine modes (RFC-0244 "Decision"; landed `engine_mode.py`).** The mode is read from the same settings snapshot the decide uses and applies at request entry; 0245 never forces a resident model out. `reflex_only` (`not model_enabled(settings)`): **no large-prompt pipeline of any kind.** `precheck` returns before any rule or probe call, so `large_prompt is None` with no rider and no candidate; the `create_task` large branch is not taken (no pipeline row, no `gate_outlook`, no preload, no lease, no ack, no vault note, no split); the turn then follows RFC-0244's own path, `_run`'s early return for a disabled model (`reflex_only_reply`), which 0245 leaves unchanged. 0232's RE floor and every other floor behave as RFC-0244 and 0232 define. `model_only` (`not decision_engines_enabled(settings)`): the pipeline runs normally **without the reflex lane**. The precheck uses only the deterministic rules L1-L5 and 0232's RE helper (no typed-provider rider, no JEV or Laya call, so a prompt only a provider would have raised to `large` stays `None`); the split mode is `sections` unless L3 fired; the ack, preload, split, completeness and queue are unchanged, because they are front and large-model work, not reflex decisions. The mode is re-read at every child dispatch and at `/continue` and recovery (§5): under `reflex_only` those steps dispatch nothing and preload nothing, and the parent shows one non-spoken event until the mode allows models again. Tests: `test_engine_mode_reflex_only_runs_no_pipeline_no_preload_no_ack` and `test_engine_mode_model_only_runs_pipeline_without_jev_laya` (S4), `test_engine_mode_reflex_only_parks_recovered_pipeline` (S5). **No snapshot (`decide_owner_turn(..., settings=None)`, legal: landed 0244 treats a settings-less decision as rules only).** `engine_mode(None)` is the `_rules_only` sentinel under which **both** `not model_enabled` and `not decision_engines_enabled` are true; the rule is that **`reflex_only` takes precedence** when both are true, so with no snapshot the precheck returns before any rule or probe call exactly as in `reflex_only`: no large-prompt rider, no candidate, no pipeline. The precheck **never calls `load_settings`** (it runs before the `engine_mode_scope` that wraps `decide`, so `engine_mode(None)` would otherwise read the file on the event loop, against 0244's "no reloading configuration" rule); 0232's RE floor and every other floor are unchanged. Test: `test_precheck_without_settings_snapshot_is_rules_only_and_never_loads_settings` (S1).
- **Output.** New field `OwnerTurnDecision.large_prompt: LargePromptIntent | None` (`OwnerTurnDecision`; `_apply_policy_guard` carries it through), with fields `verdict`, `mode`, `rules_fired: tuple[str, ...]`, `decision_source`, `confidence`. `request_routing` passes the field through unchanged.
- **#649's planner is not a second decision.** The landed auto-planner (`loop.py::AgentRuntime._run` `needs_workflow` `prepare_workflow(..., planner=MANAGER.chat)`) never runs for a pipeline parent or child (S4/S5 mark and skip, §2). When `large_prompts.enabled` is false or the verdict is `None`, #649 behaves exactly as landed.
- **Arbitration class.** The large ack is a front notice, not an answer. The parent's final result is the combined child outcome, which matches `keep_worker` semantics (`surfaces.py`). `arbitrate_front_and_worker` is not called for the ack.

### 2. Ack and preload (S4)

**Order inside `AgentRuntime.create_task`** (`loop.py`), matching #666 and #664:
1. RFC-0230 S3's `prewarm_worker("turn")` and the route decision (RFC-0230 owns that position);
2. RFC-0232's RE dispatch (an RE turn never reaches step 4, and its decision has `large_prompt=None`, §1);
3. the `Task` commit and RFC-0218 S3b's persona block (unchanged, including `publish_persona_switch_line` per #663);
4. **this RFC's large branch**, which replaces only the generic ack at `AgentRuntime.create_task` for a large turn.

**Marking the parent.** The large branch inserts the `large_prompt_pipelines` row (§4) in the same session as the `Task` commit, before `_start_runner`. That row is the mark: `large_prompt_queue.is_pipeline_parent(task_id)` reads it, and `_run` returns into the parent runner **before** `loop.py` (#649's `needs_workflow`), so #649's planner never plans a 0245 parent (CoS ruling 2). Children are seeded (§4), so `load_workflow` finds a stored plan and #649 never auto-plans them either.

**The large branch, step by step** (all in-memory, no I/O probe, so the ack stays inside its budget):
1. **Cancel 0230's 9B prewarm** when a target resolves and the gate outlook is not `refuse`: `turn_prewarm.cancel_prewarm(turn_id)` (RFC-0230 S3 exposes it; #666 S3). A prewarm that has not yet called `prepare_engine_for` is cancelled. One already inside `prepare_engine_for` finishes under its single-flight, and the preload's own gate call queues behind it. With the outlook `refuse`, the prewarm is left alone (the parts will run on the 9B).
2. **Resolve the target** (`large_prompt.resolve_target`, below) and **ask the RFC-0225 gate before wording the ack** (CoS ruling 4): `engine_coexistence.gate_outlook(target) -> GateOutlook(verdict: "resident" | "allow" | "refuse", reason: str)`, added by 0245-S0 (§2a). It reads only RFC-0225's in-memory state:
   - `resident`: the target is in `anzu_loaded_instances()` or the last `/api/ps` snapshot RFC-0225 keeps;
   - `refuse`: **all** of: the resident worker is owner-loaded (not in `anzu_loads`, e.g. Taco's LM Studio `127.0.0.1:1234` `qwen3.5-9b-defiant-fable-uncensored`), `is_managed(<its engine>)` is false, **and** RFC-0225's last free-VRAM reading is known, fresh (≤ 60 s) and below the target's requirement + 1 GB headroom (`anzu_coder.vram_requirement_gb(target)` + 1 = 15 GiB, §2a). That is the refusal in #652 §"Engine preparation path" step 5 (owner-loaded 9B, managed mode off), predicted without a probe. RFC-0225 measures free VRAM inside step 5 (#652 §"Engine preparation path" step 5, "VRAM gate for large models") but keeps no reading, so 0245-S0 adds `engine_coexistence.last_free_vram() -> VramReading | None`, recorded by every step-5 measurement (§2a);
   - `allow` otherwise, including an unknown or stale reading and any card where the 27B fits beside the resident 9B (e.g. 18 GB free on a 24 GB card): the preload runs and the real step-5 gate decides, with its refusal fallback below.
3. **Speak the one ack** (CoS ruling 5). The text is a module constant chosen from the outlook. **No variant says the larger model is loading**, so the ack can never claim a load the gate has not allowed:

   | Outlook | Text |
   | --- | --- |
   | `resident` | "This is a large task. I'll split it into parts and work through them one by one with the larger model." |
   | `allow` | "This is a large task. I'll split it into parts and work through them one by one." |
   | `refuse` | "This is a large task. I'll split it into parts and work through them on the model you have loaded." |
   | no target | "This is a large task. I'll split it into parts and work through them on the current model." |

   **Delivery is the parent's front lane (RFC-0230 rule 1, #666 §3 "Decisions", rule 1).** For a pipeline parent `_run` skips `_run_managed_front_lane` and the front-off fallback (`chat_tts` plus `publish_owner_text`). The ack **is** the parent's front-lane line, published as `BUS.publish(task.id, "acknowledgement", "Acknowledged", text, stage="queued")` (the event the 0218 S3b latency test measures) plus `BUS.publish(task.id, "chat_tts", "Large task", text, stage="large_prompt_ack")`, and stamped with RFC-0230 S0's `mark(turn_id, "tts_enqueued", lane="front", source="large_prompt_ack")`. The client's `first_audio` mark (`chatTtsPlayer.ts`, 0230-S0) closes the clock. The title is not `"Speak reply"`, so the ack never joins the reply prefix (`useTaskSpeech.ts::useTaskSpeech`). The ack never goes through `publish_owner_text` (no client, #663). It is a fixed text, not a front-model generation, because a generation could claim a load the gate refuses (ruling 4).
   **Nothing else on the parent is spoken until its terminal outcome.** The gate line, preload status, "Part n of N done", needs_owner and vault lines are `BUS.publish(parent, "large_prompt", …)` events only (visible in Show work and the panel). RFC-0225 owner lines raised by the preload carry `task_id=parent` and `speak=False` (§2a), so they show as a chip and a task event but are not spoken. The terminal outcome (combined result or failure text) is the task's answer, spoken by the existing outcome path once.
4. Record `ack_ms` on the pipeline row, then start the parent runner: `_start_runner(task.id, self._run(task.id, continue_existing=False))`, unchanged.
5. **Start the preload**, after the runner has started, with `asyncio.create_task(large_prompt.preload(task.id, target, outlook))` only when a target resolved and the outlook is `resident` or `allow`. It is not awaited, and the handle is stored on the runtime so cancel can reach it. With `refuse`, no preload runs, no model is touched, and the parent shows one event: "Running on <loaded model>: the larger model needs about 14 GiB and would need the 9B unloaded, which ANZU only does in managed mode (Settings → Local engines → Let ANZU manage this engine)."

**Order and the unload hold (normative; UX B4).** `create_task` is also called by background callers (`dispatch_next` children, the queue watcher, intake), so it never calls `IDLE_UNLOAD.touch()` itself, and #690 does not touch in `AGENT._start_runner` either (#690's `test_background_task_runner_never_clears_manually_unloaded`). The owner's act is the **entry handler**: `POST /api/tasks` (`api/tasks.py::create_task`) calls `IDLE_UNLOAD.touch()` immediately before `AGENT.create_task`, and `POST /api/tasks/{task_id}/continue` (`api/tasks.py::continue_task`) calls it immediately before `AGENT.continue_task` (#690; the voice, mobile, workflow and security-agent entry points do the same). `touch()` lifts `manually_unloaded` (and the release hold) when the engine mode can use a model, so by the time step 5 creates the preload task the flag is already clear and `MANAGER.load` respawns the 27B instead of raising `ModelManuallyUnloaded`; steps 4 before 5 additionally guarantee the parent runner exists (so a cancel reaches it and the `released:` status has a runner to land on) before the preload task's first await. A large turn that reaches `create_task` from a caller that did not touch (a background caller) finds the hold still set: its preload hits `ModelManuallyUnloaded` and ends as the existing `failed:<reason>` outcome, and `dispatch_next` then cancels the pipeline through its `warm_blocked()` check (S5); nothing respawns in the background. The rule is: only an owner turn or an explicit Load touches or respawns, with one exception owned by RFC-0246 S3 (RFC-0246 landed with #688 @ `9a544982`; CoS N2): with Keep warm ON, the single background respawn of the released seats after a studio run (RFC-0225 `prepare_engine_for`) may load, but it checks `manually_unloaded` first, is skipped when it is set, and never clears it (it calls neither `touch()` nor `explicit_load()`); 0245 adds no other background respawn. `test_large_turn_after_manual_unload_respawns_on_demand` asserts the order (the flag is already clear at the first `MANAGER.load`, and `_start_runner` is called before the preload task starts).

**Splitting runs after the ack (normative).** No split, completeness or compile work runs in `create_task`; it all runs in the parent runner, which starts after the ack is published. `test_ack_not_delayed_by_split` holds this with a split fake that blocks for 5 s.

**Latency budget (normative), on RFC-0230's clock.**
- **CI:** the ack `chat_tts` is persisted ≤ 150 ms after `evaluate_request_route` returns, with a preload fake that blocks for 5 s and a split fake that blocks for 5 s.
- **Owner-visible target:** the large turn is held to RFC-0230's target, **first audible word ≤ 1.5 s at p50 and ≤ 2.0 s at p95 from end of owner input** (#666 §2 "Target", hard target), measured with 0230-S0's marks. 0245-S4 adds three large-turn cases (`tests/fixtures/rfc0245/latency_cases.json`, from the S3 fixtures: 5-item list, 4 questions, 6000-char spec) through 0230-S0's `--cases` hook in `scripts/anzu-latency-repro.ps1`. The headline is 0230's client-clock `first_audio − input_end`, closed by the browser's `playing` event. There is no separate 0245 clock.

**Target resolution** (`agent/large_prompt.py::resolve_target(settings) -> TargetResolution`, sync, in-memory):
1. `settings.large_prompts.target_runtime` (default `"anzu-coder-27b"`, the 0245-S0 profile), matched against **enabled** runtime profiles (`list_runtime_profiles()`, `enabled is True`) by `name`, then `model_profile`, then the provider model id. A disabled row never matches (`runtime_router.py::_filter_candidates`).
2. Otherwise `route_runtime` (`runtime_router.py`) with `minimum_answer_tier=3`, `task_specialization="coding"` when `task_class` is code/build/debug and `"reasoning"` otherwise, and `preferred_profiles=("expert", "ornith_35b")` (ported from `answer_routing.py::select_runtime_for_decision`).
3. Otherwise no target, with `reason` = S0's last reconcile outcome (`anzu_coder.last_outcome()`). The parent event names it: `ollama_unreachable` → "Ollama isn't running, so the larger model isn't available; running on the current model."; `not_advertised` → "Ollama doesn't list anzu-coder-27b; running on the current model."; `owner_disabled` → "anzu-coder-27b is turned off in your runtime profiles; running on the current model." When the outcome was `ollama_unreachable` and the template is disabled, the **preload task** (never the ack path) first runs one bounded reconcile, `reconcile_anzu_coder_profile(attempts=1, timeout_s=3.0)`. If that enables the row, it re-resolves and continues with the preload, and the event says "Found anzu-coder-27b in Ollama; using it for the parts."

**Preload** (`large_prompt.preload`). No new loader, and **0245 does not edit `hotswap.py`**; it uses RFC-0225's public gate API plus existing, unedited calls:
1. **Request lease first.** `token = engine_coexistence.hold_request_lease(engine_id, model, reason=f"large-prompt:{parent}")` (§2a), held while the parent is `running` (CoS ruling 3); for `waiting`, see below.
2. **Load without persisting.** `settings = await hotswap.apply_runtime_profile_to_settings(target, persist=False)` (`hotswap.py`, existing keyword, not edited), then `await MANAGER.load(settings, profile_name, context_size=target.context_limit, task_id=parent)`. The target is the runtime profile named exactly **`anzu-coder-27b`** (`target.name`, §2a), and `apply_runtime_profile_to_settings` sets the Ollama backend and model `anzu-coder-27b` on the in-memory settings. `profile_name = target.model_profile or settings.inference.profile`; the S0 row has `model_profile = None`, so the saved profile key is kept (the same result `hotswap._resolve_builtin_profile_name` gives for this row, without calling that private helper). **Owner rebind (defined):** `rebind_owner_conversations_after_hotswap` (`hotswap.py::activate_runtime_profile`) is **not** run, because the parts are fresh child tasks bound to the target per task, and the owner's conversations keep the saved selection and its context limit (`test_preload_does_not_rebind_owner_conversations`). After RFC-0225 S3, `MANAGER.load(..., task_id=...)` forwards to `engine_coexistence.prepare_engine_for` (#652 Owner-line surfaces, item 1): single-flight, revive or respawn, identity check, step-5 VRAM gate and owner lines. `save_settings` is never called, so **a large-task load never becomes the owner's saved selection** (ruling 3).
3. Warm with `gpu_prefer.ensure_ollama_gpu` or `gpu_prefer.ensure_lmstudio_gpu` (both in `inference/gpu_prefer.py`; `ensure_ollama_gpu` is where today's hardcoded `keep_alive: "24h"` sat before #690, which replaced it with `keep_alive.ollama_keep_alive()`), by provider. For an Ollama target the preload first reads `GET /api/ps`:

**While the parent is `running`** (parts executing, and the gaps between them):
- RFC-0225 step 6 sees the held request lease and never unloads the target; step 7 never unloads during a lease (#652 §"Engine preparation path", step 5's ANZU-loaded-heavy bullet and step 7).
- **Keep-alive while a child is running (N4; CoS K2).** Ollama's `keep_alive` is Ollama-side, and the ANZU lease does not stop it, so with **Keep warm off** a long tool step with no model request could let it expire mid-part, fire #655's 27B-idle (§"Orchestrator default + one 9B re-warm path") `NINE_B_REWARM`, and ping-pong both models. The refresh therefore runs **only while a child task stage is actively running** on an ANZU-loaded target (`LeaseRecord.anzu_loaded` true, Keep warm off): every `idle_unload_seconds / 2` (150 s by default) it sends `POST /api/generate {"model": "anzu-coder-27b", "keep_alive": "<idle_unload_seconds>s"}` (no prompt) through `keep_alive.ollama_request(client, host, port, "/api/generate", "anzu-coder-27b", {"prompt": "", "stream": False})` (#690's helper, the same one the preload's warm uses inside `ensure_ollama_gpu`; it adds `keep_alive` from `keep_alive.ollama_keep_alive()` and raises `DeniedModelError` for a denied name such as `bgm-ingest-9b`, so the refresh and the warm can never address it). **#691's direct senders (a dependency, not true today):** on `development` with #691 landed, `running_models.unload_native` (`keep_alive: 0`) and `RunningModels._launch_profile` (the Manager Start's prompt-less `/api/generate`) still post to Ollama through their own `httpx` client; #690 routes both through `keep_alive.ollama_request` when it merges `development` (#686 *Reconciliation with #691* row 3, pinned by #690's `test_every_ollama_generate_and_chat_call_goes_through_the_one_helper`). Until then `keep_alive.ollama_request` is the only Ollama sender **0245** uses, not the only one in ANZU. It is not sent merely because a lease is held: not in a gap with no running child, not while the parent is `waiting`, not during a #668 capability-ask wait. **Each tick re-checks**, before sending, that (a) the target is listed in `/api/ps` (a refresh never loads), (b) `MANAGER.state.manually_unloaded` is false and the pipeline is not cancelled, and (c) Keep warm is still off; any failed check ends the refresh task. The refresh is a **background caller** (it never calls `IDLE_UNLOAD.touch()` or `explicit_load()`) and asks `idle_unload.warm_blocked()` before every send, so after an explicit Unload it can neither send nor load; its value comes from `keep_alive.ollama_keep_alive()` (no second spelling of the policy). **Entering `waiting`** stops the refresh in the same call that starts the wait timer. With **Keep warm on** the target was warmed with `"-1"`, never expires and no refresh is sent; **turning Keep warm on mid-lease re-sends `"-1"` once to every loaded ANZU-loaded target** (a leased target warmed under Keep warm off carries `"300s"` and would otherwise expire inside 300 s, then `NINE_B_REWARM` would fire), which is the global re-pin in #686's amendment (#690 sends it: `api/settings.py::update_settings` schedules `keep_warm_release.repin_loaded_models` when Keep warm turns on, which re-pins every resident `LOADED` Ollama model through `keep_alive.ollama_request` and skips when `warm_blocked()`; #686 reconciliation row 6 is met, and `large_prompt` registers no second sender); turning it off resumes the idle clock and, if a child is running, the refresh. The refresh also stops at release, terminal and cancel. A target that is not ANZU-owned (neither `anzu_loads` nor `LOADED` names it) is never refreshed. Part requests also reset the 27B's idle clock (`MANAGER.chat` / `chat_stream` call `MANAGER._mark_used()` at start and finish, which resets the model's own clock with `LOADED.touch(backend, model)` and never creates an entry, and the post-turn touch is `MANAGER._keep_alive_touch` → `keep_alive.touch_ollama_if_resident`, a native prompt-less `/api/generate` with the policy `keep_alive` that is sent only when `/api/ps` lists the model and `warm_blocked()` is false), so with Keep warm off the 27B is never idle longer than `idle_unload_seconds` after its last use, in line with #655 §"Orchestrator default + one 9B re-warm path" ("With Keep warm off the 27B is still never held longer than `idle_unload_seconds`"); with Keep warm on it stays resident until the reverse gate or the owner unloads it.
- `NINE_B_REWARM` (RFC-0228 S2, used only through its public API; 0245 does not edit `rewarm.py`) never swaps the worker between parts: 0245 calls `schedule_orchestrator_restore` only at parent terminal (restore step 3), the 27B-idle trigger fires only once the 27B has left VRAM (#655 §"Orchestrator default + one 9B re-warm path"), and any rewarm reload goes through `prepare_engine_for`, whose steps 6 and 7 never unload a target holding a request lease (#652 §"Engine preparation path", steps 6 and 7) and whose last VRAM guard skips a 9B reload that does not fit (#655 §"Orchestrator default + one 9B re-warm path", "Last guard").
- **Chat turns during a pipeline** route to the loaded target: `prepare_answer_route` uses the loaded runtime (`loop.py::AgentRuntime._run`), and the front lane still speaks first per RFC-0230. RFC-0230 S3's per-turn prewarm skips while the lease is held: 0245-S4 registers `large_prompt.active_target() -> RuntimeProfile | None` (any pipeline holding a lease) through 0230-S3's `turn_prewarm.register_lease_probe` (#666 S3), so a chat turn never issues a 9B `prepare_engine_for` against the lease and never touches the 27B. A chat turn that explicitly needs the 9B (persona brain, explicit switch) waits on the lease under RFC-0225 step 7 and gets that step's visible line.

**While the parent is `waiting`** (a `needs_owner` part; CoS ruling, same rule as #668; CoS K2): when the parent enters `waiting`, `large_prompt` stops the refresh and starts a wait timer of `idle_unload_seconds - last_model_use_age` seconds, clamped at 0 (the global `idle_unload_seconds`, default 300 s; see the global Keep warm policy (`InferenceSettings.keep_warm`, default off, and `InferenceSettings.idle_unload_seconds`, default 300, implemented by #690 (keep-warm): `inference/keep_alive.py`, `inference/idle_unload.py`, `inference/loaded_models.py`; contract in #686 (RFC-0242; final head in this PR's body) section "Amendment: Keep warm toggle and 5-minute idle unload")), so the timer ends at `last_use + idle_unload_seconds`. **`last_model_use` (defined):** its source is #690's per-model idle clock: `loaded_models.LOADED.match(backend, [model])` returns the target's `Entry`, whose `last_use` is reset by `MANAGER._mark_used()` → `LOADED.touch(backend, model)`, which `MANAGER.chat` and `chat_stream` call at the start and at the finish of every request, the child's requests included (`_mark_used` never creates an entry; `MANAGER._register_loaded` records an Ollama or LM Studio model only with `attach`, an explicit owner Load, so it is not the clock), and `LOADED.idle_for(entry)` is the age (monotonic; tests inject `LoadedModels(clock=...)`). **Fallback** when the target has no entry (a model not in `LOADED`, an entry already forgotten, or the ledger unavailable): `LeaseRecord.last_use`, a field `large_prompt` sets at lease start and refreshes in `on_child_terminal` and at every part-request finish it observes; if even that is unset, the child's terminal time. The age is `idle_unload_seconds()` and `keep_warm_enabled()` read through `inference/keep_alive.py`, never a second copy of the setting. The timer governs the lease, so it runs in both Keep warm states. Lease release and the idle unload are the **same moment**: Ollama's own `keep_alive: "300s"` from the child's last request, #690's idle clock (`LOADED.idle_for`) and this timer all end at `last_use + 300 s` (#690's `IDLE_UNLOAD.tick` polls every 15 s (`POLL_SECONDS`) and defers while an `AGENT` task is running (`is_busy`, reason `task_running`) or while a request, stream or reload holds the engine lease (`engine_leased`, `MANAGER._request_lease.in_flight`); neither check reads `large_prompt._leases`, so a `waiting` pipeline does not hold the tick back and it runs at the first poll at or after that moment, never before the timer), which means the 27B leaves VRAM `idle_unload_seconds` after its last use, **not 2x** (never 450 to 600 s). When it fires, the lease is released and, **only if ANZU loaded the target** (it has a `LOADED` entry and the lease's `anzu_loaded` is true), the target is left to the global policy's idle unload (Keep warm off: it unloads `idle_unload_seconds` after its last use; Keep warm on: it stays resident) and to RFC-0225's reverse gate; a model ANZU did not load is never touched. The 9B comes back through `NINE_B_REWARM` as usual (a background origin: after an explicit Unload it skips). `/continue` cancels the timer if it has not fired, otherwise it re-preloads (below) before the next dispatch. **A `waiting` parent after its lease was released (defined).** Once the wait timer has fired the parent stays `waiting` with `preload_status = "released:waiting_idle"` and **no `LeaseRecord`**. A later owner Unload (HUD or dropdown) therefore finds no lease to match: `on_owner_unload` does not cancel it, its sections stay as they were, and `/continue` respawns the target on demand like any owner turn (the route's `touch()` clears the flag first). While the lease is still held, the same Unload cancels it (rule 1 below). This difference is intended and tested (`test_unload_with_released_waiting_parent_leaves_it_waiting_and_continue_respawns`).

**Owner Unload and the lease (K1; CoS load-origin ruling; UX round 11).** The HUD **Unload model** button (`HudModelRelease.tsx`, #690) calls `POST /api/model/unload-all` (`api/model_unload_all.py::unload_all_models` → `keep_warm_release.release_models("manual")`; the dropdown's single-model Unload is `POST /api/model/unload`). **#690's contract, followed exactly:** 409 when nothing was attempted (an unload already running, a model still loading, the front responder starting, nothing ANZU-owned to unload, or a model request that is not part of a task still holding `MANAGER._request_lease` after the task cancel below); otherwise 200 when every model in the set was released and verified (`keep_alive: 0` plus the `/api/ps` re-check, or the LM Studio and llama-server equivalents), and 207 when some or all releases failed, with one row per model (`results`). The set is `chosen`, i.e. `LOADED`'s entries: **ownership fails closed**, so a model no ledger names (Taco's shell-started 27B, the studio's `bgm-ingest-9b`) is never released. **Tasks (today, #690):** when `IDLE_UNLOAD.is_busy()`, `release_models` calls `IDLE_UNLOAD.cancel_running` → `AgentRuntime.cancel_running_for_owner_unload`, which marks **every** running task `cancelled` (status written directly, one `cancelled` event "Cancelled: the owner pressed Unload model."), whatever model it uses. #686 reconciliation row 2 records this as "Refusal met, set membership open", and #686 T3 narrows it (`on_owner_unload(chosen)` before `cancel_running`, then cancel only non-pipeline tasks and tasks of pipelines in the set; #686's `test_unload_all_leaves_a_pipeline_whose_target_is_outside_the_set_running`). **Order (defined):** #690's nothing-attempted refusals that come first (unload already running, loading, front responder starting, nothing to unload) cancel nothing (#690's `test_nothing_to_unload_never_cancels_tasks`); then `await large_prompt_queue.on_owner_unload(chosen)` (supplied by 0245-S5; the call site in `keep_warm_release.release_models` for source `"manual"` is #686 T3's) runs **before** `cancel_running` and before the exclusive request lease. **The interface (defined):** `on_owner_unload(entries: list[loaded_models.Entry]) -> list[str]` returns the parent ids it cancelled. `entries` are #690's `loaded_models.Entry` objects (`backend`, `model`, `aliases`). A pipeline is **in the set** when `LOADED.match(_backend_of(lease.engine_id), _match_ids(lease))` returns an entry whose `key` is one of `entries`' keys (so `anzu-coder-27b:latest` matches `anzu-coder-27b`; never string equality on `LeaseRecord.model`). **`large_prompt._backend_of(engine_id: str) -> str | None` (defined, 0245-S4, `agent/large_prompt.py`):** it reads the kind of RFC-0225's engine id (`<kind>@<host>:<port>`) and maps `ollama` → `loaded_models.OLLAMA`, `lmstudio` → `loaded_models.LMSTUDIO` and `llama-server` → `loaded_models.LLAMA_SERVER`; any other kind, or an id without `@`, gives `None`, and a `None` backend is never in the set (fail closed). **`large_prompt._match_ids(lease) -> list[str]`:** `[lease.model]` for Ollama and LM Studio, and `[loaded_models.WORKER]` for ANZU's managed llama-server, which #690 records as `(LLAMA_SERVER, WORKER)` (`MANAGER._register_loaded`). A target that is not in `LOADED` is matched on a transient `Entry(backend, model)` built from the lease, and is in the set only for the dropdown call below. **Dropdown route:** `POST /api/model/unload` (single model, any loader; `api/model.py::unload_model`) also calls `on_owner_unload([entry])` for the selected model before it unloads it, with `entry = LOADED.match(backend, [model])` or the transient entry for an owner-loaded model; the call site is #686 T3's, and the effect is the same: a held lease on that model cancels the pipeline.
1. **Set membership.** For every pipeline whose target is in `entries` (matched as above): stop the refresh and the wait timer, call `on_parent_cancel(parent, reason="owner_unload")` (the existing path: the running child is cancelled through `AGENT.cancel`, whose stream releases its model request, and every remaining section becomes `cancelled`), release the lease through `release_request_lease` (`release_lease(parent)`), and set the parent to `cancelled` with `preload_status = "released:owner_unload"` and one non-spoken parent event: "Stopped the large prompt because you asked to unload the models. Send it again to run it." This applies to an owner-loaded target too when it is in `entries` (dropdown route): the preload (`MANAGER.load(..., task_id=...)`) makes the target the selected serving model, and a release must never pull it from under a running child. The pipeline's own terminal restore does **not** reload the 9B (steps 2 and 3 below are skipped when `released:owner_unload`).
2. **A running child outside the set (interim rule, until #686 T3 lands).** #690 cancels every running task, so a pipeline whose target is outside `entries` (Taco's default: a shell-started 27B that no ledger names, while the set holds only ANZU-loaded models) loses its running child anyway. That cancel is an owner Unload, not a part skip: 0245-S5 adds one line in `AgentRuntime.cancel_running_for_owner_unload` (#690's function in `loop.py`), immediately before its `self.cancel(task_id)`: `large_prompt_queue.note_owner_unload_cancel(task_id)` (sync; a no-op for a task that is neither a pipeline parent nor a pipeline child). For a **pipeline child** it resolves the parent; for a **pipeline parent** (its own runner is still alive while the pipeline is `preparing`: splitting, completeness rounds, or waiting up to `PRELOAD_DEADLINE_S` for the preload) it uses that task id as the parent. Either way it records the reason `owner_unload` for that parent, sets its `cancelling` flag and hands `on_parent_cancel(parent, reason="owner_unload")` to the main loop through the same thread-safe path as `request_parent_cancel`; `on_parent_cancel` cancels the preload task, releases the RFC-0225 lease (`release_lease(parent)`), marks every section `cancelled` and stops the refresh and the wait timer. Because the hook runs before #690's `self.cancel(task_id)`, the `request_parent_cancel` that `AGENT.cancel` then issues finds the reason already recorded and is a no-op (`on_parent_cancel` is idempotent; the first recorded reason wins). The child-cancel path (section `skipped`, dispatch the next part) is therefore never taken for it: `on_child_terminal` sees the flag, records the section `cancelled` and dispatches nothing, and the parent ends `cancelled` with `released:owner_unload` and the same non-spoken event (the owner also sees #690's `cancelled` event on the child). **No silent failure:** the cancel always reaches the owner as that parent event and the parent's `cancelled` status. The pipeline's model is released only if it is in `entries`; a model outside the set gets no unload, warm or refresh call. A pipeline with **no running task** at that moment, neither its parent runner nor a child (in a gap between parts after the parent runner returned, or `waiting` with its lease held), is not touched by `cancel_running`; it is cancelled by rule 1 when its target is in the set, and otherwise, once the release has set `manually_unloaded` or the owner-release hold, by its next `dispatch_next` through `warm_blocked()` (below). **After #686 T3:** `cancel_running` no longer cancels the child of a pipeline outside the set, so that pipeline keeps running and no unload, warm or refresh call reaches its model; `note_owner_unload_cancel` stays the hook for every pipeline parent and child T3 still cancels. **Fail closed (CoS condition 3):** `note_owner_unload_cancel` never raises into #690's loop; an internal error is logged once (`large_prompt owner_unload_hook_failed task=<id>`) and #690's cancel and the release continue unchanged. Two backstops then keep the pipeline from advancing or holding anything, and both follow the one reason precedence of §5 *Terminal hook* (UX round 13), so neither ever labels a cancel `owner_unload` unless that reason was recorded: (a) `on_child_terminal` takes the skip-and-advance path **only** for the owner's Cancel part (`note_child_cancel_api` recorded `part_skip`; precedence step 3). When the hook failed, #690's `self.cancel(task_id)` still runs `AGENT.cancel`, whose `request_parent_cancel` records `owner_cancel` for the child (or `kill_switch` while `self_dev.kill_switch_active()`), so the pipeline ends through step 4 with that reason's own text ("Cancelled.", or `failed` with the breaker text), never advanced; a child cancelled with no recorded reason at all ends the pipeline through step 5 with the neutral `child_cancelled` text. A Manager Stop's `pausing` flag (step 2) and a cancelled or `cancelling` pipeline (step 1) win over every recorded reason. (b) The parent runner's cancellation handler (`CancelledError` while `preparing`) applies the same order: `cancelling` already set or a recorded reason → `on_parent_cancel(parent, reason=<recorded>)`; the `shutdown` reason (`begin_shutdown` ran, and no per-task reason was recorded) → `release_for_shutdown(parent)`, which cancels the preload task, releases the lease (`release_lease(parent)`) and stops the refresh, but writes no terminal status, so the pipeline stays `preparing` and §5 *Startup recovery* re-runs it; no reason at all → `on_parent_cancel(parent, reason="prepare_cancelled")` with its neutral text. The preload task is therefore cancelled and the lease released even when the hook failed, and only a recorded `owner_unload` sets `released:owner_unload` or shows the unload text. Neither the hook nor a backstop sends any unload, warm or refresh request, so nothing outside `LOADED` is touched.
3. unload-all then takes the exclusive lease (a model request that does not belong to a cancelled child still returns 409 with its visible text), releases every model in the set with verification and sets `manually_unloaded` only after a fully verified release.
4. **Order and outcomes (defined).** The pipeline cancel (rules 1 and 2) happens **before** the release and is **not undone** by how the release ends: `200` (every model verified), `207` (some or all releases failed; one row per model) and `409` after the cancel (a request that is not a cancelled child still holds the lease; nothing released) all leave the pipeline `cancelled` with `released:owner_unload`. That is why the text says the owner **asked** to unload, not that models were unloaded. Nothing re-preloads it after a 207 or 409, and the owner reads the HUD's own per-model result for the release outcome. Tests: `test_owner_unload_409_after_cancel_leaves_pipeline_cancelled_with_neutral_text`, `test_owner_unload_207_after_cancel_leaves_pipeline_cancelled_with_neutral_text`, `test_cancel_running_child_outside_the_set_cancels_pipeline_as_owner_unload_not_advanced`, `test_cancel_running_preparing_parent_outside_the_set_releases_lease_and_cancels_preload` and the fail-closed tests `test_note_owner_unload_cancel_fails_closed_for_child` and `test_note_owner_unload_cancel_fails_closed_for_preparing_parent` (S5).

`on_parent_cancel(task_id, *, reason="owner_cancel")` (S5) takes the reason so the parent text, status and event differ: `owner_cancel` ("Cancelled."; the cancel endpoint, voice stop, media, the live agent suite and any other `AGENT.cancel`), `owner_unload` (the text above, `preload_status = "released:owner_unload"`), `kill_switch` (recorded by `request_parent_cancel` when `self_dev.kill_switch_active()` is true as the cancel arrives, which holds for every cancel `self_dev.activate_kill_switch` issues because it writes the stop file before it calls `AGENT.cancel`; the parent ends `failed`, like a failed part, with the existing self-dev kill-switch text naming `self_dev.kill_switch_reason()`), `child_cancelled` (a part's child cancelled with no recorded reason: "Stopped the large prompt because part n was stopped. Send it again to run it.") and `prepare_cancelled` (the parent runner cancelled while `preparing` with no recorded reason: "Stopped the large prompt while it was being prepared. Send it again to run it."). Only `owner_unload` sets `released:owner_unload` or uses the unload text. Backend shutdown is never an `on_parent_cancel` reason: `release_for_shutdown` releases the lease and leaves the pipeline recoverable (§5). The first recorded reason for a parent or child wins; every other behaviour is as before.

**After an explicit Unload (`manually_unloaded` true), the CoS ruling applies:** background paths never reload anything until an explicit Load; an owner turn respawns on demand, like after an idle unload. Concretely for this RFC:

**Re-preload on resume.** `/continue` on the parent and `recover_on_startup` (§5) check `MANAGER.state` and Ollama `/api/ps`. When the target is no longer resident or the lease was released (the `waiting` timer fired, an idle unload, backend restart), they re-run `preload` (new lease, same outcomes) before the next dispatch; `/continue` is an owner act and respawns on demand, recovery is a background origin (see *After an explicit Unload* above). A pipeline cancelled by an owner Unload is terminal and is never re-preloaded.

**Restore at pipeline end** (any terminal parent status):
1. Release the request lease (if still held). The target's `keep_alive` is already the global policy's value (`"<idle_unload_seconds>s"` or `"-1"`), so nothing else is sent. When `preload_status == "released:owner_unload"` the restore ends here: no reload, no `schedule_orchestrator_restore`.
2. **Restore the owner's selection.** Because the preload never persisted, `load_settings().inference` is still the owner's selection. If `MANAGER.state` still points at the target the pipeline loaded, the restore calls `MANAGER.load(load_settings(), <saved profile>, task_id=parent)`, which goes through `prepare_engine_for`, i.e. RFC-0225 step 6 unloads the ANZU-loaded target when the 9B needs the room, and never unloads an owner-loaded one. If the owner changed the model meanwhile (through settings, which merge via `_merge_settings_changes`, `config.py`, used at `save_settings._write`), `MANAGER.state` no longer points at the target and nothing is restored.
3. Call `schedule_orchestrator_restore` (`model_escalation.py`; after RFC-0228 S2 that is `NINE_B_REWARM`).

### 3. Split, completeness, compile (S3)

All of this lives in `agent/large_prompt_intake.py` (new). It runs in the parent runner, deterministically, on CPU, and does not wait for the preload.

**Split** (`split_prompt(text, mode) -> SplitResult`):
- **sections mode:**
  - Split boundaries are, in priority order: Markdown headings, top-level numbered or bulleted items, then blank-line paragraphs. This reuses `decision/intake.py split_segments` for paragraph segmentation.
  - Text before the first boundary is the **shared context** (preamble). A trailing paragraph that begins "Constraints", "Requirements", "Note", "Let op" or "Eisen", or that contains no boundary marker after the last item, is the **shared constraints** block (trailer).
- **questions mode:** one section per question sentence. Non-question sentences that sit between questions attach to the following question as context.
- **Bounds:**
  - 1 ≤ N ≤ `MAX_SECTIONS = 8`, the same value as `intake.MAX_SEQUENTIAL_PARTS`.
  - When N > 8, the two smallest adjacent sections are merged repeatedly.
  - A section under 40 chars is merged into its predecessor.
  - N == 1 is valid: the pipeline still runs one detailed prompt with sub-tasks.
- **Ingress.** A prompt over 6000 chars stores the original once with `memory/ingress_spill.store_ingress_blob` (its `token_estimate` comes from `inference/prompt_budget.py::estimate_text_tokens`). Every section then carries the blob reference so the child can `read_ingress`. The `maybe_mirror_to_vault` swallow is not used.

**Completeness** (`check_section(section, ctx) -> Completeness`):
- Deterministic criteria:
  - **C1, actionable:** at least 3 words and at least one verb or question.
  - **C2, no dangling reference:** "it", "that", "the above", "dit", "dat" or "hierboven" as the subject, without a referent in the section or the shared context.
  - **C3, deliverable inferable:** an imperative verb or a question exists.
  - **C4 (questions mode):** the section is interrogative.
- A Reflex decide scores each section per round: `decision_class="verifier_score"`, the 50 ms deadline, and `choice complete | incomplete` with a `missing` rationale. Rules are the fallback.
- A section is **complete** when C1-C4 pass and the score is not `incomplete` at confidence ≥ 0.75.
- **Deterministic repairs, one per round, in this order:**
  1. merge into the predecessor (fixes C2 or C1);
  2. merge with the next section;
  3. attach the previous section's text as context (fixes C2).

  Each repair is recorded in `repairs_json`.
- **Hard bound: `MAX_COMPLETENESS_ROUNDS = 3`.** At the bound the outcome is **defined**:
  - The section status becomes `needs_owner` and `missing_json` lists the failed criteria.
  - One parent event (not spoken; CoS ruling 5): `Part N isn't clear enough to start: <missing, ≤ 120 chars>. Tell me what you mean, or say "skip part N".` The parent's `waiting` status shows it in the panel and the task list.
  - The queue runs every part **before** the blocked one, then the parent goes to `waiting`.
  - An owner reply via `/continue` on the parent sets that part's `source_text` to the original text plus the reply, and grants exactly **one** more round. Failing that round re-asks once with the same line. "skip part N" marks the part `skipped`.
  - Nothing proceeds on an incomplete section. Nothing soft-fails.

**Compile** (`compile_prompt(section, ctx) -> str`, deterministic template, ≤ 6000 chars; #649's brief budget at `task_workflow.py::prepare_workflow`):

```
Part {n} of {N}: {title}
Goal: {one-line goal, the first sentence of the section}
Shared context: {preamble, ≤ 1200 chars, or "read_ingress <blob>" reference}
Constraints: {trailer, verbatim}
Section (verbatim): {source_text}
Deliverable: {inferred deliverable, or "a direct, complete answer to the question"}
Acceptance: {the section's own success criteria if stated, else "every point in the section is addressed"}
Rules: do only this part; earlier parts' results are given below when relevant; report what could not be verified.
```

At dispatch, the child gets `Previous part result (≤ 1800 chars)`, which is intake's `CARRYOVER_CHARS`. No model rewrites the section text. The detailed prompt is reproducible from the row.

**Mandatory sub-tasks (every prompt, always).** The child's workflow steps are:
1. `work`;
2. `deeper`;
3. `quantitative`;
4. then #649's `REVIEW_STEPS` when `large_task_reviews` is on.

`deeper` and `quantitative` are not toggleable.

- **deeper** step prompt: analyse the part's result beyond the direct answer. The result **must** contain these Markdown headings:
  - `Root cause / mechanism`;
  - `Alternatives considered`, with at least 2 items;
  - `Assumptions checked`;
  - `Edge cases`.
- **quantitative** step prompt: put numbers on it. The result **must** contain:
  - a Markdown table with header `Metric | Value | Unit | Source/Method`;
  - at least 1 row with a numeric Value;
  - in every row, either a source (file, command, URL or measurement) or `estimate: <method>`;
  - a line beginning `Acceptance:` that states the target against the measured or estimated value.

  When the part is genuinely non-numeric, the row is `Measurable criteria | <count> | items | enumerated above`, which still holds a number.
- **Validators** (`validate_deeper`, `validate_quantitative`, pure): a failed validation re-runs the step with the validator's message appended, at most **2 retries**. After that the step fails, and the part fails visibly with "Part n of N: quantitative sub-task did not meet its format after 3 attempts". No validator is skipped.

**Persist.**
- SQLite is **always** authoritative: `large_prompt_pipelines` plus `large_prompt_sections` (§4).
- **Vault mirror:** applies when `public_binding_status` (`memory/obsidian_vault.py`) is bound and `large_prompts.store == "db_and_vault"`. It is **idempotent, keyed on the section's `vault_rel_path`** (`_Temporal/LargePrompts/<parent_id>/part-NN.md`):
  - **get-or-create:** when the row already has `vault_rel_path` and the note exists, it is reused; only otherwise `create_note` writes it with frontmatter (parent, ordinal, status) and the detailed prompt. `create_note` raises `FileExistsError` on an existing file, so a recovery re-dispatch or a follow-up recompile never calls it twice; an existing file without a row path is adopted and its path stored.
  - **append, not replace:** `edit_note` replaces the body, so at part terminal the pipeline reads the current body, composes `<existing body>\n\n## Result\n<summary>` and passes that to `edit_note`. A recompile appends `## Prompt (revised)` the same way.
- **Owner-edit conflict:** `edit_note` reports a conflict without `force`. The pipeline does not force. It records `vault_conflict` on the row and shows one parent event (not spoken), "Part n note was edited in Obsidian; ANZU left your edit and kept the result in ANZU".
- **Mirror failure:** produces a visible parent event (not spoken). DB persistence and the run continue.
- `large_prompts.store` takes the values `"db"` (default) or `"db_and_vault"`.

### 5. Queue and lifecycle (S5)

This reuses the semantics of `agent/intake.py`'s chain (stable ids, advance on terminal, stop on failure; `part_request_id, start_sequential_chain, advance_chain`), moved from JSON files to the DB, and admits each child through the same breaker scheduled runs use.

- **Dispatch** (`large_prompt_queue.dispatch_next(parent_id)`):
  - Under a per-parent `asyncio.Lock`, pick the lowest-ordinal `pending` or `queued` section.
  - **Unload check first:** `idle_unload.warm_blocked()` (true while `MANAGER.state.manually_unloaded` or the owner-release hold is set). When it is set, `dispatch_next` calls `on_parent_cancel(parent, reason="owner_unload")` and creates no child: a child created by `create_task` would reach `_load_impl` as a background caller and fail with `ModelManuallyUnloaded`, or (from a caller that touched) respawn a model nobody asked for. `create_task` and `AGENT._start_runner` do not touch (#690), so no child can lift the hold.
  - Call `admit_automatic_trigger` (`automation/breaker.py`) with automation id `large-prompt:<parent>`, `ensure_automation` first. When the kill switch is engaged or the breaker is open, the parent fails visibly with the breaker reason. No retry loop.
  - Call `AGENT.create_task(child_prompt, request_id=uuid5(NS, f"large-prompt:{parent}:{ordinal}"), pipeline_section=section_id, profile=target)`.
  - The id is stable, so a re-dispatch after a crash reuses the same child (`loop.py::AgentRuntime.create_task` request_id reuse).
  - **A requeued part re-runs on its child.** `create_task` with an existing `request_id` returns that row unchanged unless it is `queued`, so for a section whose `child_task_id` names a child that is already `cancelled` (requeued by the Manager Stop pause, precedence step 2, or interrupted by shutdown, §5 *Startup recovery*) `dispatch_next` calls `AGENT.continue_task(child_id)` (no prompt: the child's stored workflow resumes, `continue_existing=True`) instead of `create_task`, after the same breaker admit and `bind_run_to_task`. It is a background call and never touches.
  - **Bind the admitted run to the child:** `bind_run_to_task(run_id, child.id)` (`automation/breaker.py`) right after `create_task` returns, the same call the scheduler makes (`mobile/scheduler.py::tick`). Without it the admitted run stays in flight and eats the failure budget (`breaker.py::_in_flight_run_count`, `admit_automatic_trigger`). A re-dispatch that reuses the child id re-binds the same run id.
- **`create_task(..., pipeline_section: str | None = None)`**, keyword-only, default `None`, so every existing call is unchanged. When it is set:
  - The route is fixed to MANAGED with the parent's task class and **no decide** (the parent turn already decided; still exactly one decide per owner turn).
  - No persona block, no large branch (no recursion) and no generic ack.
  - `seed_workflow` with `work, deeper, quantitative, *REVIEW_STEPS?` runs in the same session as the Task commit, before `_start_runner`.
  - The title is `Part n of N · <section title ≤ 60 chars>`.
- **`_run` for a child:** skip the managed front lane and its `chat_tts`. Children never speak, because the HUD follows the parent. Run the seeded workflow on the target profile. Per-child `speak_outcome` in the terminal hook is suppressed.
- **Terminal hook** (`_update`), placed next to `advance_intake_chain`, as `large_prompt_queue.on_child_terminal(child_id, status, result)`. It is idempotent per child: the first call that records the section wins (a running child's own `_update` hook and `on_child_cancel_api` can both arrive). **Reason precedence for a `cancelled` child (normative, UX round 13; first match wins):**
  1. **Pipeline cancelled:** `pipeline.status == "cancelled"` or its `cancelling` flag is set → the section is `cancelled` and the hook returns; it never dispatches (the parent cancel owns the text and event).
  2. **Manager Stop pause:** the pipeline's `pausing` flag is set (`on_manager_stop`) → the section goes back to `pending`, nothing is dispatched, and the parent is `waiting` with `released:manager_stop` (§2 *Reconciliation with #691*, row 2). This wins over the `owner_cancel` that `AGENT.cancel` records for the child.
  3. **The owner's Cancel part:** `note_child_cancel_api` recorded `part_skip` for this child (`api/tasks.py::cancel_task`, before its `AGENT.cancel`) → section `skipped`, parent event "Part n skipped", dispatch the next part.
  4. **A recorded reason, each on its own path:** `kill_switch` → `on_parent_cancel(parent, reason="kill_switch")` (parent `failed` with the breaker text); `owner_cancel` (voice stop, media, the live agent suite, or any other `AGENT.cancel` of the child) → `on_parent_cancel(parent, reason="owner_cancel")` ("Cancelled."); `owner_unload` (normally caught by step 1 through hook 1's `cancelling` flag) → `on_parent_cancel(parent, reason="owner_unload")` (the unload text); `shutdown` (`begin_shutdown` ran and no per-task reason was recorded) → `release_for_shutdown(parent)`: the lease is released and the refresh and wait timer stopped, and nothing is written, so the section stays `running`, the pipeline keeps its status and §5 *Startup recovery* re-runs the part.
  5. **No recorded reason** (a runner cancelled without `AGENT.cancel`, `on_child_cancel_api` or shutdown, or with `request_parent_cancel` itself failing) → `on_parent_cancel(parent, reason="child_cancelled")`: fail closed, never advanced, with the neutral text "Stopped the large prompt because part n was stopped. Send it again to run it.", never the unload text.

  Any other child status:

| Child status | Effect |
| --- | --- |
| completed | Section `completed` with `result_summary`; vault append (§3); parent event "Part n of N done" (not spoken); dispatch the next part. If the next part is `needs_owner`, the parent goes to `waiting` and shows the line once as an event; the request lease stays held. If there is no next part, the parent completes. |
| cancelled through the owner's Cancel part only (`on_child_cancel_api`, precedence step 3; pipeline not cancelled and not pausing) | Section `skipped`; parent event "Part n skipped"; dispatch the next part. Every other cancel follows the precedence above. |
| failed | Section `failed`; remaining sections `cancelled`. The parent **fails** with "Part n of N failed: <error ≤ 200>. Parts n+1–N were not started." That text is spoken by the existing outcome path. |
| kill switch / breaker | Same as failed, with the breaker reason (a kill-switch cancel of a running child arrives as precedence step 4, `kill_switch`; a kill switch or open breaker at the next part is `dispatch_next`'s `admit_automatic_trigger` refusal). |

- **Parent completion:**
  - `result` is the per-part Markdown sections ("## Part n: title" plus result).
  - `verification` has one line per part: the part's own verification, plus "deeper ✓ quantitative ✓".
  - Status is `completed`. The existing `speak_outcome` and the `useTaskSpeech` final speech run unchanged: that is the task's answer, the only parent speech after the ack.
  - Then the restore (§2).
- **Parent runner:**
  1. Run intake (§3).
  2. Await the preload up to its deadline.
  3. Set parent status `running` with `current_action` "Part 1 of N".
  4. Dispatch.
  5. **Return without a terminal status.** The parent stays `running` (or `waiting`), driven by the hook.

  `_update`'s terminal hook therefore never sees a parent until the pipeline itself sets it terminal.
- **Cancel:**
  - `AGENT.cancel` (`loop.py`) is **sync** and stays sync. S5 adds one call in it: `large_prompt_queue.request_parent_cancel(task_id)` (sync, a no-op for a non-pipeline task). **Reason recording (UX round 13):** it first records the cancel reason for that task unless one is already recorded (the first wins): `kill_switch` when `self_dev.kill_switch_active()` is true, otherwise `owner_cancel`. For a pipeline **child** it only records that reason (so `note_child_cancel_api`'s `part_skip`, set earlier, and a Manager Stop's `pausing` flag still win) and returns; `on_child_terminal` then applies the precedence. For a pipeline **parent** it sets an in-memory `cancelling` flag that `on_child_terminal` and `dispatch_next` treat exactly like `pipeline.status == "cancelled"`, then hands `on_parent_cancel(task_id)` to the event loop **thread-safely**: on the loop thread with `loop.call_soon(loop.create_task, …)`, from any other thread with `asyncio.run_coroutine_threadsafe(…, loop)`, where `loop` is the backend's main loop captured by `large_prompt_queue.bind_loop()` in `main.py`'s startup, **immediately before** `recover_on_startup`. **Before `bind_loop` has run** (a startup-time cancel, or a test that never binds a loop) `request_parent_cancel` only sets the `cancelling` flag and logs one line `large_prompt cancel_before_bind task=<id>`. It never raises and schedules nothing. `dispatch_next` honours the flag (no dispatch; it runs `on_parent_cancel` itself, which marks the pipeline `cancelled`), and `recover_on_startup` honours it the same way for a pipeline it would otherwise resume. This works whether or not the parent runner is still alive (it returns after the first dispatch, so its handler cannot be relied on). Every sync caller therefore reaches a running pipeline: the cancel endpoint (`api/tasks.py::cancel_task`), voice stop (`mobile/realtime_voice.py::interrupt_turn`), media (`mobile/media.py::VoiceBridge.accept_audio`), self-dev (`agent/self_dev.py::activate_kill_switch`) and the live agent suite (`inference/live_agent_suite.py::_run_live_suite`). `POST /api/tasks/{id}/cancel` (`async def cancel_task`, `api/tasks.py`) for a pipeline parent additionally **`await`s `large_prompt_queue.on_parent_cancel(parent)`** first, then calls `AGENT.cancel(parent)` and commits the row as today. `on_parent_cancel`, under the per-parent lock, sets `pipeline.status = "cancelled"` **first**, then cancels the running child and the preload task, marks the rest `cancelled`, cancels the `waiting` timer and the keep-alive refresh, releases the lease and runs the restore. It is idempotent, so the scheduled call after the endpoint's awaited one is a no-op. The running child's later terminal hook sees the cancelled pipeline (or the flag) and never dispatches.
  - For a pipeline **child**, `cancel_task` keeps its order (sync `AGENT.cancel`, then the `status = "cancelled"` commit without `_update`, so the terminal hook would never fire for a queued child with no runner) and S5 adds two calls: one sync call **before** `AGENT.cancel`, `large_prompt_queue.note_child_cancel_api(child_id)`, which records `part_skip` for that child, so whichever terminal call arrives first (the running child's own `CancelledError` → `_update` hook, or the call below) takes precedence step 3; and one call after that commit, `await large_prompt_queue.on_child_cancel_api(child_id)`, which runs `on_child_terminal(child_id, "cancelled", None)` (skip that part, dispatch the next).
  - **Backend shutdown:** `main.py::shutdown` calls `large_prompt_queue.begin_shutdown()` (sync, never raises) as its first line. From then on a pipeline task cancelled without its own recorded reason gets `shutdown`: a `preparing` parent runner's handler calls `release_for_shutdown(parent)` (preload task cancelled, lease released, refresh stopped) and writes no terminal parent status, so the parent and the pipeline stay recoverable as `preparing`; a running child's terminal hook takes precedence step 4 (`shutdown`) and leaves its section `running`. Nothing is made terminal by a shutdown.
- **Follow-ups:**
  - `/continue` on a **child** is redirected to the parent, in `continue_task`.
  - `/continue` on the **parent** is handled in `_run`'s follow-up path, after S3b's follow-up persona block. It first re-preloads when the target is no longer resident (§2). If a part is `needs_owner`, the reply answers it (§3). Otherwise the text is appended as a new last part (content-hash dedupe, the same rule as landed `append_followup`, `task_workflow.py`; the parent has no stored workflow, so `append_followup` itself is not called) and goes through completeness and compile.
- **Startup recovery** (`main.py`, after `reconcile_execution_on_startup`). A pipeline in **`preparing`** (the parent runner died before compile/persist, or a backend shutdown cancelled it and `release_for_shutdown` left it `preparing`) re-runs the parent runner from intake: split, completeness, compile and persist are idempotent (§3, uq(`parent_task_id`, `ordinal`)), then the preload if no lease is held. For each pipeline in `running` or `waiting`:
  - **`running` only:** re-take the request lease (`large_prompt._leases`);
  - **`waiting` pipelines take no lease and preload nothing**: the parent is waiting for the owner, so loading a 14 GiB model at startup would contradict "respawn on demand", load something that idles out 300 s later and may evict the 9B through the gate. `/continue` is the owner act that respawns the target (`test_recovery_preloads_only_running_pipelines_waiting_resumes_on_continue`);
  - for a `running` pipeline, when the target is not resident, re-run `preload` (§2 "Re-preload on resume"; recovery is a background origin and a pipeline with `preload_status == "released:owner_unload"` is terminal and skipped);
  - if the current section is `running` and its child is `cancelled`, the part was interrupted by shutdown (every other cancel moves the section off `running` in `on_child_terminal` before the process exits): set the section back to `pending` and `dispatch_next` re-runs it on the same child through `AGENT.continue_task` (§5 *Dispatch*);
  - otherwise, if the current child is `completed` or `failed`, run `on_child_terminal` (a missed advance);
  - if it is `queued` without a runner, dispatch it again (same id);
  - if it is `running` without a runner, call `continue_task(child)`, which resumes the durable run (RFC-0029).
- **Visibility:** `get_task` (`api/tasks.py`) **and** `get_task_observability` (`api/tasks.py`, which `TaskActivity.tsx::TaskActivityPanel` fetches once, only while `phase_history` is empty; live parent updates come from `GET /api/tasks/{id}`) both gain the same `large_prompt` object (one builder, `large_prompt_queue.payload(task_id)`), containing:
  - mode;
  - status;
  - target;
  - preload_status;
  - ack_ms;
  - sections (`ordinal`, `title`, `status`, `completeness`, `rounds`, `missing`, `child_task_id`, `vault_rel_path`, `vault_conflict`).

  Parent events are plain human text, so Show work (`OwnerChatTranscript.tsx::OwnerChatTranscript`, which renders `title` and `detail`) shows the progress without an edit.
- **Recents:** children appear in `/api/tasks` (polled by `App.tsx::OwnerPortal`) with their "Part n of N" titles. The list endpoint is unchanged.

## Overall acceptance

- [ ] A large spoken or typed prompt gets exactly one spoken ack on the parent's front lane, persisted ≤ 150 ms after the decision (CI) and held to RFC-0230's ≤ 1.5 s p50 / ≤ 2.0 s p95 first audible word (live audit), worded from the RFC-0225 gate outlook so it never claims a load the gate did not allow.
- [ ] A path plus RE intent goes to reverse engineering and is never split; a path with a plain or coding question routes normally.
- [ ] Size detection uses the full prompt, also on the deadline and exception fallbacks.
- [ ] The prompt is split, every section is complete or explicitly `needs_owner` within 3 rounds, and each section becomes one detailed prompt stored in SQLite (and idempotently in the vault when enabled).
- [ ] The parts run strictly one after another on a target that no background path unloads until the parent is terminal (an owner Unload cancels the pipeline visibly; a Manager Stop pauses it at the part boundary); the large-task load is never saved as the owner's selection, and the owner's selection is back afterwards.
- [ ] On Taco's default (LM Studio 9B owner-loaded, managed mode off, 16 GB) the parts run on the 9B with an honest ack and the task completes; nothing ANZU did not load is unloaded.
- [ ] Every part has validated deeper and quantitative sub-tasks, and the parent shows progress, can be cancelled, and ends with a combined, verified result.
- [ ] With `large_prompts.enabled=false`, behaviour is identical to today, including #649's planner.
- [ ] RFC-0244 engine modes: under `reflex_only` a large prompt starts no pipeline, preload or ack and gets RFC-0244's model-required reply; under `model_only` the pipeline runs with a rules-only precheck and no JEV or Laya call (named tests in S4/S5).
- [ ] The HUD Unload model button follows #690's 200 / 207 / 409 contract and fails closed on ownership; during a lease it cancels the pipeline visibly and releases the ANZU-loaded 27B, and until #686 T3 lands a pipeline whose running child #690 cancels is cancelled as `owner_unload`, never advanced; after an explicit Unload no background path reloads anything, a new large turn or `/continue` respawns on demand, and under `reflex_only` nothing loads (named tests in S4/S5).
- [ ] 0245-S5 is implemented only after #690 has landed on `development`; its two CoS-approved hooks (#690 `AgentRuntime.cancel_running_for_owner_unload` → `note_owner_unload_cancel`, #691 `RunningModels.decide` → `on_manager_stop`) each fail closed: a failing hook never blocks the cancel or the stop, touches nothing outside `LOADED`, and never lets the pipeline advance or reload (named tests in S5). ## Risks

- **27B load time over 180 s on a cold disk.** Mitigation: defined fallback plus owner line. The deadline is a module constant, so it is tunable after the live audit.
- **Deterministic split mis-sections free prose.** Mitigation: completeness repairs and the owner `needs_owner` loop. N == 1 is always valid.
- **The quantitative format feels forced on qualitative parts.** Mitigation: the "Measurable criteria" row keeps the format honest without inventing numbers.
- **A cancel shown with the wrong reason** (UX round 13). Mitigation: one precedence in `on_child_terminal` and the parent runner's handler; reasons are recorded where the cancel starts (`note_owner_unload_cancel`, `note_child_cancel_api`, `request_parent_cancel` with `self_dev.kill_switch_active()`, `begin_shutdown`); an unrecorded cancel gets neutral text, never the unload text, and a shutdown never makes a pipeline terminal.
- **Collisions in `loop.py`.** Mitigation: the strict ownership chain above, with two 0245 slices (S4, S5) in sequence after landed #649.

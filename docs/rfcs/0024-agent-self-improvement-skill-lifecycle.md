# RFC-0024: Agent self-improvement skill lifecycle

**Status:** accepted  
**Queue item:** P4 — adaptive intelligence / skill promotion  
**Author:** ChatGPT competitor-watch synthesis  
**Date:** 2026-08-31

## Problem

Jarvis can learn from trajectories and promote repeated workflows, but it does not yet define a safe lifecycle for an agent to propose, test, version, activate, and roll back its own reusable skills or harness-level adaptations. Letta's recent direction around self-managed skills, git-tracked agent context, and harness-level Mods shows the value of allowing agents to improve their execution layer without changing the underlying model. Unbounded self-modification would be unsafe, difficult to audit, and hard to recover from.

## Decision

Add a governed `SkillCandidate` lifecycle that turns verified execution experience into versioned skills without permitting direct in-place mutation of active production behavior.

A candidate may originate from repeated successful trajectories, explicit user instruction, a Memory Maintenance Agent, or an agent-authored improvement proposal. Every candidate stores provenance, intended scope, required capabilities, generated files/config, expected benefit, tests, verifier results, and rollback metadata.

Lifecycle: `PROPOSED -> SANDBOXED -> VERIFIED -> APPROVED -> ACTIVE`, with terminal/alternate states `REJECTED`, `SUPERSEDED`, `ROLLED_BACK`, and `QUARANTINED`.

Generated or modified skills execute first in an isolated test environment using representative fixtures/trajectories. Activation must never silently broaden authority: the effective capability set is the intersection of the skill declaration, parent Agent Profile policy, current task policy, and node/runtime policy. High-risk skills or harness modifications require Decision Inbox approval even when generated by an L4/L5 agent.

Keep skill content versioned and immutable after activation; edits create a new version. Preserve previous active versions for one-click rollback. Record measured before/after success rate, latency, cost, retries, and verifier outcomes so Jarvis can automatically recommend rollback when a new version regresses.

## Acceptance criteria

- [ ] Add a persistent `SkillCandidate`/`SkillVersion` model with source trajectory/proposal IDs, scope, required capabilities, files/config, status, created-by agent, test evidence, and rollback target.
- [ ] Candidate creation never modifies an active skill in place.
- [ ] New or changed executable skill content runs in an isolated sandbox before activation.
- [ ] A verifier must produce a structured pass/fail result against declared acceptance tests before status may become `VERIFIED`.
- [ ] Activation computes effective permissions as an intersection with existing Jarvis policy; a skill can never grant itself new authority.
- [ ] Harness-level modifications, credential-touching skills, destructive capabilities, external publishing, or financial actions require explicit approval unless an existing narrowly scoped policy explicitly permits that exact class.
- [ ] Active versions are immutable; updates create a new version with parent-version provenance.
- [ ] Rollback restores the prior active version without deleting evidence from the failed version.
- [ ] Jarvis stores comparison metrics for old vs new versions and can flag statistically/operationally meaningful regression.
- [ ] UI shows proposed, verifying, active, quarantined, and rollback-able skill versions with source evidence and effective permissions.
- [ ] Existing P4 learning controls can disable self-generated skill proposals independently of ordinary memory learning.
- [ ] Unit tests pass (`python3 -m pytest`).
- [ ] If portal is touched, `npm --prefix frontend run build` passes.

## Out of scope

Training or fine-tuning models; fully autonomous source-code changes to Jarvis core; public skill marketplace; cross-cluster skill distribution; replacing RFC-based development governance for Jarvis itself.

## Problem

Verified on the `development` tip when this amendment was pushed.

1. **Only the old studio is reachable.** `tools/blackgrid_studio.py::BlackGridStudioTool` drives a local ComfyUI HR Endless sampler through `studio/blackgrid_runtime.py` (port 8188, `BlackGridSettings` in `config.py`). It cannot reach the new Black Grid Multimedia Studio (local FastAPI on `127.0.0.1:8745`), which has a story bible, durable pipeline runs, streaming book ingest, Wan2.2 clip generation, review and a final stitch (BGM #32-#34).
2. **The tool is nearly unreachable in the live path.** The live loop uses `agent/tool_exposure.py` (`tool_names_for`, `schemas_for`). Its `CLASS_TOOLS` and `CAPABILITY_ALIASES` do not mention `blackgrid_studio`, and `agent/tool_retrieval.py::_SEARCH_TERMS` has no entry for it. Only the older `tools/exposure.py::TASK_TOOL_SETS` lists it (used by `agent/local_harness.py`). In practice the model reaches it only by calling `request_tools` with the exact name.
3. **No policy for studio actions.** `policy/reversibility.py::resolve_action_effect` knows nothing about `blackgrid_studio`, so every action falls into the generic medium-risk path. A multi-hour render and a read look the same to the gate.
4. **ANZU and the studio fight for 16 GB.** The studio's Wan2.2 clip runs need almost all of a 16 GB card. ANZU's models (front and worker seats, LM Studio or llama.cpp instances loaded by ANZU) stay resident, and nothing on `development` checks whether another application is rendering before a model is loaded by `InferenceManager.load`, by `FrontRuntime.ensure_started`, or by the direct warms that bypass both (`ollama_runtime.ensure_local_ollama` with its HTTP warm, `gpu_prefer.ensure_ollama_gpu`, `gpu_prefer.ensure_lmstudio_gpu`, `lmstudio_server.ensure_local_lmstudio`). The first symptom is a CUDA out-of-memory error halfway through a long render.
5. **The studio cannot say "the GPU is busy".** At the traced heads there is no endpoint that reports it. Runs are listed **per project** (`GET /api/projects/{project_id}/pipeline/runs`), and the legacy JSON-clip flow's jobs (`GET /api/jobs/{job_id}`, kinds `generate`, `video`, `image`, `stitch`) have no list endpoint at all. Run status alone is also the wrong signal: PG confirms a **paused** run still holds the Wan weights today, and a later Pause may release them. That is a studio-side gap (BGM-P1, with the fields PG named: `wan_loaded`, `active_run`, `paused`, `vram_mb`).

## Decision

Ship **one RFC with five implement slices (S1-S5)**, one named model per slice, fast mode off, plus **two studio-side PRs** that belong to the BGM repo and PG's review.

```
owner / model turn ─► agent/tool_exposure.py (alias + retrieval, S2) ─► ToolRegistry.execute("blackgrid_studio", action="studio_*")
        │                                   │
        │                                   ├─ gate: policy.reversibility.resolve_action_effect (new branch, S2) ─► ApprovalGrant for expensive/destructive actions (RFC-0031/0110)
        │                                   └─ BgmClient (S1, loopback only, fixtures-conformant) ─► http://127.0.0.1:8745/api/...
        │
        └─ before ANZU loads ANY model: StudioGpuGate.check (S3) ─► BGM-P1 GET /api/gpu/status (keys on wan_loaded / active_run / ingest_llm.loaded)
              busy ─► defer the load with a visible reason (explicit owner Load: refused, 409)
              free / studio not running ─► load as today
        run starts (seen by poll, or started through this tool) ─► verified release of ANZU-loaded models (#686 T3 path) ─► hold + visible reason
        run ends ─► hold cleared ─► respawn on demand by the next owner turn (`keep_warm` true: one BACKGROUND respawn of the released seats via RFC-0225 `prepare_engine_for`, skipped when `manually_unloaded` is set or the owner pressed Unload during the hold)
```

**One tool path, not a parallel one.** The connector is extra actions on the existing `blackgrid_studio` tool (same registry entry, same `ToolRegistry.execute`, same gate, same exposure code). There is no new tool class, no MCP server and no second HTTP layer.

`GpuStatus` (BGM-P1, from PG's workers; **the four field names `wan_loaded`, `active_run`, `paused`, `vram_mb` are PG's, the rest of the shape is proposed and PG's PR sets it**): `{"contract_version": 1, "wan_loaded": bool, "active_run": {"project_id", "run_id", "stage", "status": "running|paused", "cursor", "total"} | null, "paused": bool, "vram_mb": int, "ingest_llm": {"endpoint", "model", "loaded": bool}, "stitch_uses_gpu": false, "checked_at": iso}`.

**The gate's busy rule (normative).** `busy = wan_loaded OR (active_run.stage == "generate" AND active_run.status == "running") OR ingest_llm.loaded`. It keys on `wan_loaded` and `active_run`, **never on run state alone**: a `paused` run with `wan_loaded == true` is busy (PG: a paused run still holds Wan today), and a `paused` run with `wan_loaded == false` is **free**, so on the day a later BGM Pause releases Wan, ANZU frees the hold on its next poll with no ANZU change. A running `generate` run that has not loaded Wan yet (lazy load) is busy because it is about to. `ingest` is busy only while its LLM (`ingest_llm`, `bgm-ingest-9b` in Ollama) is loaded; `stitch` is CPU ffmpeg (libx264) and never holds the GPU, which P1 states as `stitch_uses_gpu: false` (any other value is a `StudioContractMismatch`). `vram_mb` is shown in the hold text and never used to decide. ANZU never reads run lists for this.

**Stage rules the connector relies on** (from `GenerateStage` / `StitchStage` / `PipelineRunner`):
- `generate` renders with Wan2.2 TI2V-5B when `GenerationConfig.video_backend == "wan"` (default); `video_backend == "ffmpeg"` is the no-GPU fallback (then `wan_loaded` stays false). `ingest` calls the studio's LLM, which PG confirms is **`bgm-ingest-9b` in Ollama** (not LM Studio, not ANZU's 9B; the PR text said the default `Settings.llm_base_url` is LM Studio, superseded by PG's answer; P1 exposes the real endpoint and model). `stitch` is CPU ffmpeg (libx264) and never holds the GPU (C6).
- One active (running or paused) run per project (`pipeline_one_active` unique index), so a second start answers 409 (`BibleConflict`).
- `stitch` needs every non-orphaned prompt approved with a take (`StitchStage.prepare`); readiness is `GET .../movie`.
- **Do not use** the legacy JSON-flow routes (`POST /api/projects/{pid}/stitch`, `.../clips/{cid}/generate`, `GET /api/jobs/{job_id}`). The connector's `studio_start_stitch` means the **pipeline stage** `stitch` via `POST .../pipeline/runs`, never the legacy `POST /api/projects/{pid}/stitch` that has the same word in its path (C7).

## 2. The connector client (S1)

`backend/app/studio/bgm_client.py::BgmClient` is the only code that talks to the studio.

- **Loopback only, enforced twice.** `config.BlackGridSettings` gains `studio_api_enabled: bool = True` (**default on**: the connector is loopback only, Taco wants ANZU to call the studio, and when no studio is running the tool says so plainly; the field is a kill switch kept in `settings.json`, documented in `TOOLS.md`, and `false` makes every studio action answer "The Black Grid Studio connector is switched off in settings (studio_api_enabled)" with no network call and no watcher poll), `studio_api_url: str = "http://127.0.0.1:8745"`, and a Pydantic validator that rejects anything else. `BgmClient.__init__` re-validates, so a settings file edited by hand cannot bypass it. Accepted hosts are exactly `127.0.0.1`, `::1` and `localhost` (normalised to `127.0.0.1`), scheme `http` only, no userinfo, no path other than empty or `/`. It deliberately does **not** reuse `tools/safety.py::is_owner_local_host`, which also accepts RFC1918 and `.local` hosts.
- **No detours.** `httpx.AsyncClient(follow_redirects=False, trust_env=False, timeout=...)`, so a proxy variable or a redirect cannot carry a call off the loopback interface. A 3xx answer is an error.
- **Timeouts.** Read calls 5 s, writes 15 s, the upload streams the file in 1 MiB blocks with a 300 s total. Studio steps run on the studio's own thread, so these calls never wait for a render.
- **Studio not running is a result, not an exception.** Connection refused (and only that) returns `StudioNotRunning` and the tool answers `{"studio": "not_running", "detail": "Black Grid Multimedia Studio is not running on 127.0.0.1:8745. Start it from its folder (studio/start.ps1) and ask again."}`. Timeouts, 5xx and malformed bodies are different, named errors (`StudioTimeout`, `StudioError`, `StudioContractMismatch`) with the studio's own detail text, which reaches the model only inside the fence (*Identity, privacy and untrusted text*, rule 3).
- **Contract conformance.** Every response is parsed by the mirrored Pydantic models with `extra="ignore"` for new optional fields but **required fields missing or a wrong type raises `StudioContractMismatch("<endpoint>: <field>")`**; the tool shows the endpoint and field names verbatim (ANZU-generated text) and any studio `detail` fenced. `GET /api/contract` is read once per session and **validated before any write and before any upload byte is sent** (see *Identity, privacy and untrusted text*): `contract_version` must be `1` (the version this RFC was written for; CI pins the whole answer in `tests/fixtures/bgm/contract.json`, S5), and every endpoint of the client registry must be listed in its `endpoints`. Otherwise every action but `studio_status` answers "studio contract version N is not supported by this ANZU" or names the missing endpoint.
- **Recorded fixtures.** `scripts/record_bgm_fixtures.py` (run locally by PG or on VRPC against a running studio; CI never starts a studio) calls each endpoint of §1 and writes `tests/fixtures/bgm/<endpoint-slug>.json` plus `tests/fixtures/bgm/manifest.json` (endpoint, method, BGM `main` description, recorded date). The conformance test replays them, so CI needs no studio for it.
- **Files stay in ANZU's policy.** `studio_upload_source` takes an absolute path that must resolve through `tools/safety.py::resolve_allowed_path` against `live_allowed_directories(...)` (the same allow-list the filesystem tool uses), and the extension is checked before any byte is read.

### Identity, privacy and untrusted text (S1 and S2)

ANZU sends file bytes and book text to whatever listens on `127.0.0.1:8745`, and everything the studio sends back is derived from a book the owner (or someone else) wrote. Three rules:

1. **The contract is validated before any upload (S1).** `BgmClient.upload_source` and every write call `ensure_contract()` first: `GET /api/contract` must succeed, `contract_version == 1`, and every endpoint ANZU uses must be listed (the same set S5 pins). A failure sends **no byte** and answers `StudioContractMismatch` (or `not_running`). This is the only identity check a loopback port can have today (BGM has no auth), so it runs once per session and again after any connection error.
2. **The ingest model's endpoint is shown and loopback-checked (S2); the only studio strings allowed into a popup are sanitised.** `studio_start_ingest` and `studio_upload_source` read BGM-P1's `ingest_llm.endpoint` and `ingest_llm.model` (the gate's last snapshot, refreshed by the tool; no network call in the sync gate branch). The `studio_start_ingest` approval popup shows the model and the endpoint and says that the book text goes to it; the `studio_upload_source` result shows them. **Both are shown only through the sanitisers of `studio/untrusted.py` (rule 3's exception):** `safe_endpoint(url)` parses the value with `urllib.parse.urlsplit` and returns **`host:port` only** (no scheme, userinfo, path, query or fragment; the host must match `[A-Za-z0-9.:-]{1,253}` or a bracketed IPv6 literal, the port must be an integer 1-65535, else the endpoint is unreadable), and `safe_model_name(name)` returns the name only if it matches `[A-Za-z0-9._:/-]{1,64}`, else it is unreadable. **A non-loopback endpoint (any host other than `127.0.0.1`, `::1`, `localhost`) refuses both actions**, and so does an unreadable `ingest_llm` (including an unreadable endpoint or model name; fail closed), with the plain text "The studio's ingest model points at <host:port>, which is not on this PC; ANZU will not send a book there." (or, for an unreadable value, "The studio reported an ingest model ANZU cannot show safely; ANZU will not send a book there."). The tool re-reads the endpoint after the grant and refuses if the sanitised pair differs from the one the popup showed, so the owner never approves a pair that changed.
3. **Studio-returned text is untrusted data, on every model-visible channel (S2).** Every free-text field the studio returns (entity names and descriptions, prompt text, proposals, remarks, error `detail`) is wrapped by `studio/untrusted.py::fence_studio_text`: a fixed delimiter block labelled as studio data, with any delimiter lookalike inside the text neutralised, and a one-line header that it is data from a book-derived record and never an instruction. **The fence applies to all three channels that reach the model: `ToolResult.data`, `ToolResult.output` (the summary string) and `ToolResult.error`.** The existing tool puts the studio's `detail` text straight into `error` (`StudioError`, `StudioTimeout`, `StudioContractMismatch` text and a project title in a summary); S2 routes every `ToolResult` the tool returns through one builder, `studio/untrusted.py::finish_tool_result(result)`, which fences each studio-derived span in `output`, `error` and `data` and passes ANZU-generated text (fixed sentences, ids, counts, statuses, run progress) unchanged; the tool never concatenates raw studio text into `output` or `error`. **Exception for popups and hold text (the only one):** approval popups and the hold text (§4) are built from ANZU's own fields, plus exactly three studio-supplied strings, each sanitised and never fenced as an instruction, because they are rendered by ANZU in its own template: the ingest endpoint as `host:port` only, the ingest and owner-model name restricted to `[A-Za-z0-9._:/-]{1,64}` (anything else is replaced by "(name not shown)" in a hold text and refuses the ingest actions in a popup), and a project title treated as plain text with control characters stripped, whitespace collapsed, double quotes turned into single quotes and the length capped at 60 characters (with "…"). Entity names, descriptions, prompts, remarks and error `detail` never appear in a popup. (There is no shared tool-output fence in `backend/app` today, so S2 adds this one module; it adds no new confirmation mechanism.)

- **Paused but still holding Wan:** `BlackGrid Studio's run is paused but still holds the GPU (Wan is loaded).`
- **Ingesting** (`active_run.stage == "ingest"` and `status == "running"`, model loaded): `BlackGrid Studio is ingesting a book (its model bgm-ingest-9b is loaded). ANZU's models stay unloaded until it finishes.`

Free it in Black Grid Studio, or run "ollama stop bgm-ingest-9b", and ask again.` (The model name in the text is P1's `ingest_llm.model` through `safe_model_name`; when it does not match the allow-list the text says "the studio's ingest model" instead of a name, and the `ollama stop` hint is omitted.) This variant names no run and gives the owner the exit, because ANZU may not unload the studio's model and the explicit Load answers 409 while it is resident.

Jev and Laya are CPU deciders and keep answering reflex turns during a hold; only generative turns see the reason.

**Unload on run start: one rule for every run stage that loads a model (`generate` and `ingest`).** Two triggers, one action, identical results:
- *Started through ANZU:* `studio_start_generation`, `studio_regenerate`, `studio_start_ingest`, and a `resume` of a `generate` or `ingest` run (the tool reads the run's stage at execution time; `stitch` and `clip_import` release nothing), after the grant and **before** the `POST`, calls `keep_warm_release.release_models("studio", targets)` (#690's verified release) for **every `LOADED` entry that is not a studio model, front seat included** (`targets = [e.key for e in LOADED.entries() if not StudioModelGuard.is_studio_model(e)]`). If the release is not verified (`refused` or `ok` false in #690's result: a request or load in flight, the front starting, a failed backend) or ANZU is mid-answer (`MANAGER._request_lease.exclusive()` not acquired, which `release_models` reports as refused), **the studio run is not started** and the tool says why. Nothing is half-started. For `ingest` and `generate` the tool also opens a **start hold** from the `POST` until BGM-P1 shows the run no longer `running`, or shows the model loaded (then the normal busy rule takes over), or 120 s pass with neither (the run failed to start); the start hold closes the gap before the studio lazily loads its model, so ANZU cannot load its own 9B in between.
- *Started from the studio's own UI:* a watcher polls BGM-P1 every `STUDIO_WATCH_INTERVAL_S = 10` while any ledger model is resident, backs off to `STUDIO_WATCH_BACKOFF_S = 60` while the studio is `not_running`, and polls nothing when no ledger model is resident, no hold is active, and `studio_api_enabled` is false. On `free → busy` (including `ingest_llm.loaded` turning true) it runs the same verified release.

A tool-started ingest and a UI-started ingest therefore both release ANZU's models and both hold, with the same text (`test_ingest_start_through_tool_and_through_ui_behave_identically`).

The release is #690's `keep_warm_release.release_models` (the function behind `POST /api/model/unload-all`; S3 calls it with `source="studio"` and has **no enumeration of its own**). It uses the **verified native path** only (LM Studio `loaded_instances` check, Ollama `/api/ps` check, managed process stop). Because the source is `"studio"` and not `"manual"`, `release_models` **does not set `manually_unloaded`** (it sets it only for `source == "manual"`), which is exactly the studio-hold rule: the flag means "stays unloaded until explicit Load" and belongs to an owner Unload; a studio hold never sets it and never clears it (only an explicit Load or an owner turn clears it). It is **not** recorded as an idle unload (`engine_coexistence.idle_unloaded()` of RFC-0228); it is its own reason, `studio_hold`, reported only after the same verified evidence (R5). `release_models` calls `IDLE_UNLOAD.note_released(front=..., owner=(source == "manual"))`: **only an owner Unload sets `IDLE_UNLOAD.held`**; a studio or idle release leaves `held` false (it calls `clear_hold()` itself). So **there is no `held` for `source="studio"`** (CoS ruling: #690 stays unchanged, S3 does not ask D2 for one), `warm_blocked()` and `background_blocked()` are false after a studio release unless `manually_unloaded` is set, and `IDLE_UNLOAD.front_released` stays true until an owner turn (`touch()`) or an explicit Load (`explicit_load()`) restarts the front. What keeps background starters off after a studio hold is therefore **S3's own rule, not `held`**; it is specified in the next subsection. A hold clears itself. When an idle unload already released the models, run start finds nothing resident, releases nothing and still holds.

**What keeps background starters off after a studio release (CoS ruling; tested).** One predicate, `StudioGpuGate.background_blocked()`, in S3's own file, and three cases:
1. **While the studio is busy** (P1 `active_run` / `wan_loaded`, `bgm-ingest-9b` resident, or the start hold): every S3 guard on a load, warm, restart or send (kinds 1 to 4) refuses, for every origin except that an explicit owner Load answers 409 with the reason.
2. **Once the studio is idle**, normal respawn on demand resumes: an owner turn (`touch()`) or an explicit Load (`explicit_load()`) restarts the front and loads what it needs, and nothing in S3 is involved. The one thing S3's own release stops that a background timer would otherwise revive is the **front responder**, so the two 0230-S2 paths (the watchdog restart of a dead front server and the 10-minute front keep-warm request) **also** treat `IDLE_UNLOAD.front_released` as blocked, and stay blocked until an owner turn or an explicit Load lifts it or the Keep-warm-ON respawn below has put the front back (S3 records that in `studio_hold`, because #690 does not reset `front_released` on a respawn). That rule applies to those two paths only, not to `ensure_started`, `_start_local` or `_warmup`, which the Keep-warm-ON respawn itself must pass. A released front is therefore not restarted behind the owner's back with Keep warm OFF.
3. **Keep warm ON**: the respawn is the one background path allowed to run after the hold. It checks `manually_unloaded` (and `warm_blocked()`) first and does nothing when either is set; it is a **background origin** (it never calls `touch()` or `explicit_load()`, so it can never clear `manually_unloaded`, and only an explicit Load or an owner turn clears it); it asks `prepare_engine_for` for the released seats once.

**Origin rule, shared with #665, #668 and #686.** Only an owner-turn origin touches or respawns on demand; a background origin never does, and a background `AGENT._start_runner` never calls `IDLE_UNLOAD.touch()`. S3 adds no `touch()` or `explicit_load()` call, no call into `_start_runner`, and no new respawn other than case 3, which is #686's Keep warm contract ("After an explicit Unload") applied after a studio hold. S3's own tool-started actions (`studio_start_*`) run inside an owner turn, but S3 does not use them to lift anything.

`test_no_background_reload_after_studio_release_with_keep_warm_off` (Keep warm OFF, the studio run ends and the studio is idle, no owner turn yet): the 0230-S2 watchdog restart and the 10-minute keep-warm request start and send nothing, the `RUNNING_MODELS` poll and the other background starters add no model of their own accord while the hold is active and follow #690's origin rule afterwards, and the next owner turn restarts the front through `touch()`.

**Targets come from the ANZU ledger only, `keep_alive` follows #686 row 4, and the name guard is #690's (CoS ruling, UX 3, 5 and 9).** #690's code is ledger-only by design (`test_ownership_comes_from_the_ledger_not_from_a_model_name`). **(a) Unload, release and warm targets.** The target set of S3's release, of #690's idle-unload and unload-all path, and of every standalone warm or load is `LOADED` (Terms), with **zero requests to anything else**. None of them enumerates `/api/ps` or `loaded_instances` and unloads what it finds, so **any model ANZU did not load is never touched, whatever its name**: `bgm-ingest-9b`, Taco's LM Studio 9B, or an unknown owner model. **A model ANZU attached to but did not start is exempt and is never idle-unloaded** (CoS ruling): attaching (routing requests to it) does not put it in the ledger, so the idle timer, the unload-all button and the studio release cannot see it. **(b) `keep_alive` on a chat request** is #686's contract, reconciliation row 4, which CoS ruled is canonical and which D2 builds in #690: **every Ollama chat request ANZU sends carries `keep_alive` through the one helper (`keep_alive.request_extras` / `ollama_keep_alive`), including a request routed to a model ANZU did not load, with `bgm-ingest-9b` denied** (no `keep_alive`, no request). This is contract C3 (`request_extras` returns `keep_alive` for every non-denied loopback Ollama model, ledger or not, and `{}` for a denied one) and C4 (`ollama_body` / `ollama_request` are the one sender), proved by S3's conformance tests; S3 does **not** narrow it back. Setting `keep_alive` on a request is not an unload and not a warm, so (a) and (b) do not conflict. The second layer, the name guard for `bgm-ingest-9b`, **lands through #690** (`keep_alive.DENIED_MODELS` and `keep_alive.is_denied()`, used by `keep_warm_release` and `keep_alive.request_extras`; contract C8, proved by S3's conformance tests; #690 stays unchanged). **S3 adds no guard call to #690's files and has no `STUDIO_INGEST_MODEL` constant.** S3's own `StudioModelGuard.is_studio_model(endpoint, model)` lives in `studio/gpu_gate.py` and serves S3's own decisions only (the hold-text wording, the owner-loaded-model notice, the target filter before it calls `release_models`): it matches P1's `ingest_llm.endpoint` and `ingest_llm.model` **or** `keep_alive.is_denied(model)` (#690's constant, no second copy of the name), so the skip holds even while the studio is down or P1 is unreadable. S3 keeps the tests that exercise the #690 guard as **conformance tests** (`test_name_guard_is_a_second_layer_even_when_the_ledger_lists_bgm_ingest_9b`, `test_gate_and_keep_warm_idle_unload_both_skip_bgm_ingest_9b`, `test_no_keep_alive_is_ever_sent_for_bgm_ingest_9b`); they pass only once #690 has landed with the guard. ANZU **never unloads `bgm-ingest-9b` and never sets `keep_alive` on it** (PG ruling 3, matching CoS's ruling to D2). **Owner-loaded models are left alone and the hold message is shown** (PG ruling 3): ANZU leaves them running, and the hold text adds `LM Studio's model "<id>" is still resident because you loaded it; unload it from the model menu to give the render the whole GPU.` using the existing explicit Unload (RFC-0244 inventory is read-only; ANZU stops no other program); `<id>` passes through `safe_model_name`.

**Respawn after the run (a background path).** The watcher's next poll sees the busy rule false (`wan_loaded` false, no running `generate` run, ingest model unloaded) (or `not_running`, which includes a studio crash) and clears the hold, publishes the cleared state, and does **nothing else** except the optional respawn below (and the guard rule "What keeps background starters off" stays in force for the front's two 0230-S2 paths). The next **owner turn** loads on demand through the normal path (origin `owner_turn`, which clears `manually_unloaded`). The optional respawn exists only with **Keep warm ON** (`InferenceSettings.keep_warm` true), and it is a **background path** (it never calls `IDLE_UNLOAD.touch()` or `explicit_load()`, so `warm_blocked()` and `_guard_background_load()` apply to it; #686's section "After an explicit Unload" is the citation, and contract C7 in *Mapping to #690* covers `touch()`'s fail-closed flag lift), so:
- The release records `released_seats`, exactly the seats it released. The respawn does **not** call `clear_hold()` (a studio release already leaves `held` false); it first checks `manually_unloaded` and `warm_blocked()` and runs nothing when either is set, then asks RFC-0225 `prepare_engine_for` for those seats and nothing else, once, never through a private loader. `prepare_engine_for` does not exist in #690's tree; it is 0225-S3, a gating item, so S3 targets it (not #690's `MANAGER.load`) when it starts.
- **It is skipped whenever `manually_unloaded` is set**, and whenever the owner pressed Unload (single or all) at any time during the hold or between the release and the run's end: S3 hooks the two unload routes, `api/model_unload_all.py` (#690's HUD **Unload model**) and the single-model Unload in `api/model.py` (`studio_hold.note_owner_unload()`), which drops the seats from `released_seats` and records `respawn_cancelled` even when the route answers 409 "Nothing to unload" (`release_models("manual")` returns that refusal without setting `manually_unloaded` when `LOADED` is empty, which is the case after the studio release). The Unload answer then names the studio: `Nothing to unload: ANZU's models were released for the Black Grid Studio render. Keep warm will not reload them afterwards because you pressed Unload; your next request loads them again.`
- The respawn **never clears `manually_unloaded`** and the hold never sets it. Only an explicit Load or an owner turn clears it. Under `reflex_only` there is no respawn at all.
- ANZU-originated Ollama warms after it use #690's `keep_alive.ollama_keep_alive()` (`"-1"` when on, `"300s"` when off, from `idle_unload_seconds`). With Keep warm OFF (default, `idle_unload_seconds` 300) there is no preload and the normal idle timer applies to whatever loads next.

## 5. Network and auth

- **Loopback only (S1).** See §2. Nothing in ANZU listens for, proxies or forwards studio traffic; there is no ANZU route that exposes BGM bytes.
- **Remote use goes through ANZU's existing auth.** A phone or LAN companion reaches the studio only by sending an ANZU task or chat turn. That request is authenticated by `auth.authenticate_request` / `require_owner_private_key` (the owner private key; loopback is the owner console, LAN/companion callers need the key) and by the computer-permission checks, exactly like every other tool. The studio's own port is never published. **PG ruling:** BGM has no auth today and token auth is required in BGM before any non-loopback use, so the connector stays loopback only (S1 guard) and this RFC adds no auth code.
- No studio credential is stored by ANZU in this RFC. If BGM-P3 (future, BGM-side token auth) ships, the token goes in the vault (`vault` / `get_effective_private_key` pattern), never in `settings.json`, and lifting the loopback-only rule needs its own RFC amendment.

## Risks

- **BGM is still moving.** #33 and #34 are stacked and open, and P1/P2 stack after #34. Mitigation: the gate, the re-trace at assignment, the contract-check items, recorded fixtures and the pinned contract (which PG refreshes); a drift fails a named test and is fixed in an amendment, not worked around.
- **BGM-P1's final shape is PG's.** Only `wan_loaded`, `active_run`, `paused` and `vram_mb` are fixed; `ingest_llm` and `stitch_uses_gpu` are proposed. If PG's PR differs, only S3's parser, S1's model and the pinned fixture change; the rule "the gate reads one studio answer, keyed on `wan_loaded` and `active_run`, never on run state alone" stays.
- **Owner-loaded models keep VRAM.** Taco's LM Studio 9B is not ANZU-loaded, so ANZU will not unload it (PG ruling 3). The studio does not use it. The hold text says so and offers the existing explicit Unload.
- **Studio hangs while up.** `unknown` defers automatic loads rather than risk the render; explicit owner Load is never blocked by `unknown`. The one confirmed-busy case with no ANZU-side exit is an idle resident `bgm-ingest-9b` (ANZU may not unload the studio's model); its hold text names no run and tells the owner the exit (Black Grid Studio, or `ollama stop bgm-ingest-9b`).
- **#690 is open and may move; this RFC states what it needs as contracts, not as its current text.** #690 (keep-warm; by number and symbol only) is canonical for names and stays unchanged for this RFC (CoS ruling), and S3 consumes its `LOADED`, `release_models`, `warm_blocked()`, `_guard_background_load()`, `keep_alive` helpers and `IDLE_UNLOAD.front_released`. *Mapping to #690* lists ten contracts (C1-C10), each with one S3 conformance test, among them ledger ownership (C6), the fail-closed turn-entry flag lift (C7), the name guard (C8) and the lease deferral (C9). S3 depends on no #686 reconciliation row being open or closed: #686 and #682 may re-trace their own table against #690 independently. If #690 changes a name or a behaviour before it lands, the failing conformance test says which contract moved, S3 re-traces at assignment, and no spec text depends on a line number.
- **Shared Ollama.** `bgm-ingest-9b` lives in the same Ollama ANZU may use. The primary protection is that unload, release, idle unload and every standalone warm act only on the ANZU ledger (`LOADED`), so a model ANZU attached to but did not start is exempt and never idle-unloaded; `keep_alive` on chat requests follows #686 row 4 (every Ollama request, `bgm-ingest-9b` denied), so an owner-started Ollama model still gets Ollama's policy value; the name guard (`keep_alive.is_denied`, #690) is the second layer, so a P1 outage or a corrupt ledger entry cannot make ANZU touch the studio's model. #690 has no `/api/ps` enumeration of its own; if a later change adds one, the ledger-only filter is the fix and `test_release_and_warm_targets_come_from_the_ledger_only` is the proof.
- **Decision (CoS, 2026-11-03): #690 stays unchanged, with no `held` for `source="studio"`.** A studio release leaves `IDLE_UNLOAD.held` false (contract C2 in *Mapping to #690*); D2 is not asked to keep it set. The reason: under the origin rule (only an owner-turn origin touches or respawns; a background origin never does), background paths do not respawn after a release, and S3's guards gate the only two paths that could: the 0230-S2 watchdog restart (and its keep-warm request), which also treat `IDLE_UNLOAD.front_released` as blocked, and the Keep-warm-ON respawn, which checks `manually_unloaded` first and never clears it (§4 "What keeps background starters off after a studio release"; test `test_no_background_reload_after_studio_release_with_keep_warm_off`). This is a deliberate decision, not an open question; changing it needs a new CoS ruling and an amendment.
- **Approval fatigue.** Approve-take is gated by design; if Taco wants "approve all ready takes" as one grant, that is an amendment with a bulk target, not a gate bypass.

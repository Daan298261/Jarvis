# ANZU model reuse, RFC scheduling and manager recovery

Date: 2026-10-09. Source baseline: development `0cdc7752`. This review addresses the owner's recovered request, not a general architecture audit.

## Running model reuse

Implemented in RFC-0210: local server discovery, owner choices, persistent use/leave decisions, worker attachment and conversation preservation. The resident front/voice seat remains independent so an unknown external worker does not consume it. Discovery is read-only, bounded, and off the health/chat request paths. Startup can wait for an owner choice instead of allocating another worker's VRAM. Busy llama slots block switching/stopping; unknown activity is labelled and the owner must confirm that a coding agent has finished.

Aider is a client, not the server supplying its model: [Aider's model connections](https://aider.chat/docs/llms.html) and [Ollama configuration](https://aider.chat/docs/llms/ollama.html). Reuse the underlying inference endpoint. Antigravity also supports local model clients in its [SDK documentation](https://www.antigravity.google/docs/sdk/local-models/); that does not establish that the owner's installed Antigravity/Cursor exports an inference API. Discovery cannot manufacture one or reuse a subscription/session as an API credential. Paid/remote provider integration remains an explicit provider configuration or a separate coding-harness adapter.

Ollama inventory uses `/api/ps`, which lists running models, rather than downloaded models: [official API](https://github.com/ollama/ollama/blob/main/docs/api.md#list-running-models). Ollama's internal llama worker is excluded from discovery. Modern LM Studio instances are identified through [its native model inventory](https://lmstudio.ai/docs/developer/rest/list) and unloaded using [the instance unload API](https://lmstudio.ai/docs/developer/rest/unload). Older servers without a safe stop method expose Use/Leave and explain that stopping must happen in their own app. API unload must be independently verified before replacement.

Read-only Windows observation during this session: LM Studio exposed a loaded Qwen3.5 9B at port 1234; Ollama exposed `anzu-coder-27b:latest` at 11434. An internal Ollama llama-server on a random port prompted the parent-process exclusion. No live models, coding clients or installed ANZU processes were stopped or switched for this check. These observations are not a real-chat or installed-release sign-off.

## Scheduler: current behavior and missing RFC workflow

`backend/app/mobile/scheduler.py` supports once/daily/weekly schedules tied to paired devices. It uses stable request IDs for each occurrence, waits for previous tasks to finish, and uses the existing automation breaker. It submits a stored prompt; it does not read a repository, select an accepted RFC, watch GitHub issues, or guarantee a coding worktree.

`backend/app/agent/queue_watcher.py` ingests prompt files and submits agent tasks. It moves accepted files to processed and failed ones to failed. This is task intake, not an RFC scheduler, and submitting a prompt alone does not establish the isolated coding mission or independent CI gate. A crash between task creation and file movement is also a duplicate-submission boundary to address before unattended RFC intake.

`backend/app/agent/self_dev.py` creates a trial worktree, records baseline tests, checkpoints, and evaluates a verification gate. `start_trial()` then waits for tasks; it does not implement a supervisor that selects and executes RFCs. Its synchronous Git/test operations are invoked directly by the async self-dev endpoints and should move to a background job before scheduled use. `agent/worktrees.py` resolves an existing local Git checkout; accepting a GitHub URL needs explicit clone/fetch handling first. RFC-0155 remains accepted, with uncompleted coding-mission acceptance criteria.

Recommended next implementation ticket: repository-backed coding mission intake under RFC-0155. Owner selects the repository and eligible ticket set; ANZU checks its instructions, checks out latest `development` in an isolated worktree, and reserves exactly one accepted ticket. Key a durable reservation by repository identity, source commit and RFC content hash. Reject implemented/draft tickets and duplicate RFC numbers with conflicting paths. Existing RFC filename collisions make bare RFC numbers insufficient identifiers. Queue one mission, run the repo's required tests/build/lint, publish an inspectable branch/diff and PR against `development`, and record completion only after its policy-approved landing. Bugfix tickets use the same mechanism with a reproducible trigger and regression test. Reuse the current breaker, budgets and emergency stop; preserve the user's dirty checkout. Resume reservations and failed CI without duplicate pushes/PRs. Installer promotion and `development` to `main` remain separate actions.

The scheduler review is complete; that new RFC selection/mission supervisor is not implemented in this discovery PR. No unattended schedule was created: the original request supplies neither a cadence nor a policy for automatically choosing/merging arbitrary future tickets. A manual Scan/Run entry point should precede recurring runs and live coding acceptance.

## Manager: independent recovery and embedded model decision

`backend/app/manager/main.py` already checks core health on 4780 and starts/stops/restarts via the Windows scripts independently of the core's FastAPI lifecycle. It does not have an automatic repair watchdog, a last-known-good installation swap, or a coding model. It still imports shared `config` and `hardware` from the same shipped Python tree, so a syntax/import/dependency failure there can disable the manager too. Independence must include packaging and environment, not just a separate port.

The current recovery journal covers policy, workflow, settings and pack state (`backend/app/recovery/types.py`). It is not a binary/source installation rollback, and core-hosted recovery cannot fix a backend that fails before the recovery route imports.

Recommendation: ship a minimal manager supervisor in its own verified runtime and update track, with independent logs and a restricted recovery tool interface. First collect launch exit codes/logs, recognize known failures, stop only ANZU-owned processes, restore a verified last-known-good payload and restart with bounded attempts/backoff. Keep owner data outside installation swaps. Validate candidate updates in a separate directory and core port before promotion; verify payload hashes and maintain a durable update transaction so a interrupted swap can resume. Detect a failure to restore rather than reporting a healthy recovery. Test missing modules, broken imports, process crashes, bad frontend assets, installer interruption and manager survival with the core deliberately broken.

An optional small CPU coding/diagnosis model can analyze logs and propose a patch in an isolated repair worktree when deterministic recovery fails. It must use the independent runtime and structured filesystem/Git/test tools, preserve diffs and test evidence, and only promote a repaired payload under the configured owner policy. The existing front seat is useful inspiration, but sharing the broken core's process/runtime defeats the recovery objective.

Do not embed an always-resident computer-use model by default. Service restart, log collection, Git repair, package checks and payload rollback have deterministic APIs/commands. A vision model adds RAM/latency and UI-state dependencies without repairing the manager's shared-package failure boundary. Evaluate an on-demand computer-use fallback only for recovery steps lacking an API/CLI, using the existing perceive/action/verify contract (RFC-0145), measured success/latency and isolated permissions. This is an engineering recommendation from the observed control paths, not a benchmark claim about a particular model. No manager repair/model feature is claimed implemented here.

## Validation

A separate baseline run restored the unmodified development versions of both changed backend integration files and also timed out; its log is preserved. The Amazon Ads file passed in isolation on a separate baseline run, so this is not a reliable Amazon logic regression diagnosis. Full-suite acceptance is not claimed. No tests were disabled and no unrelated Windows/test harness changes were committed. Installed/live acceptance remains separate: metadata discovery is not a live spoken interaction, real model chat, or installer smoke test.
